# RAG 分块策略

> 日期: 2026-06-16

## 1. 分块的重要性

分块配置对检索质量的影响 **≥ 嵌入模型的选择**（Vectara NAACL 2025）。典型失败场景：50 页合同问"终止条款是什么"，检索器返回封面页——因为终止条款跨页断裂，且与查询没有本地关键词关联。这是分块问题，不是嵌入模型问题。

## 2. 六种分块策略对比

| 策略 | 原理 | 优势 | 劣势 |
|------|------|------|------|
| **固定分块** | 每 N 字符/token 切一刀 | 最简单，压缩率好 | 句中断裂，连贯性差 |
| **递归分块** | 按分隔符优先级回退：`\n\n` → `\n` → `.` → 空格 | 2026 默认选择，兼顾大小和边界 | 极端长句仍需降级到固定分块 |
| **语义分块** | 嵌入每个句子，相似度骤降处分割 | 保持主题连贯 | 慢；可能产生 40 token 碎片 |
| **句子分块** | 按句子边界切分 | 成本极低，5k token 内接近语义分块效果 | 对长句子无能为力 |
| **父子文档分块** | 小子块检索 + 大父块提供上下文 | 检索精准 + 上下文充分 | 去重父块是关键细节 |
| **后期分块** | 先全文 token 级嵌入，再池化为块向量 | 保留跨块上下文 | 计算量大，需长上下文嵌入器 |
| **上下文检索** | LLM 为每个块生成位置摘要作为前缀 | 检索提升 35-50%（Anthropic） | 索引成本高 |

## 3. 2026 年基准测试的反直觉发现

- **递归 512 token 击败语义分块**：Vectara 实验准确率 69% vs 54%
- **重叠通常无用**：SPLADE + Mistral-8B 实验显示零收益，却让索引成本翻倍
- **上下文悬崖**：约 2,500 token 上下文时响应质量急剧下降

"显而易见"的配置（语义分块 + 20% 重叠 + 1000 token）通常是错误的。

## 4. 块大小匹配查询类型

| 查询类型 | 推荐块大小 | 原则 |
|---------|-----------|------|
| 事实型（"CEO 叫什么？"） | 256-512 token | 够包含答案+本地上下文即可 |
| 分析型/多跳型 | 512-1024 token | 需要跨句推理空间 |
| 整节理解 | 1024-2048 token | 需要完整上下文 |

块应**大到包含答案+本地上下文**，**小到让 top-K 聚焦答案而非噪声**。

## 5. 递归分块的核心实现

递归分块是 2026 年默认选择，核心思路是**按分隔符优先级优雅回退**：

1. 先尝试按 `\n\n`（段落）分割
2. 段落太大 → 按 `\n`（行）分割
3. 行太大 → 按 `.`（句子）分割
4. 句子太大 → 按空格分割
5. 全部失败 → 降级到固定分块

关键逻辑：遍历分割后的 parts，如果单个 part 超过 size 限制，递归调用下一级分隔符；否则尝试合并到缓冲区，超限则输出当前缓冲区。

## 6. 语义分块的关键参数

`threshold`（相邻句子余弦相似度阈值）是需要调参的核心：

- **太高** → 碎片化，产生大量小片段
- **太低** → 一个巨大块，失去分块意义

必须设置 **`min_chars`**（最小长度限制），防止产生 40 token 的碎片损害检索效果。超过 `max_chars` 的块要降级到递归分块。

## 7. 父子文档分块的去重细节

检索时用子块嵌入匹配查询，返回对应的父块。关键实现细节：**多个子块可能映射到同一个父块**，需要按 `parent_idx` 去重，否则重复返回浪费上下文窗口。

## 8. 上下文检索（Anthropic 模式）

对每个块，让 LLM 生成 50-100 字的文档位置摘要（如"此块是终止条款第 3.2 节..."），拼接到块前再索引。查询时检索器能利用额外的上下文信号提升匹配质量。代价是索引时需要 N 次 LLM 调用。

## 9. 五大常见陷阱

1. **只在事实型查询上评估** → 多跳查询暴露不同赢家，需分层评估
2. **语义分块不加最小长度限制** → 碎片损害检索
3. **盲目加重叠** → 2026 研究发现通常无收益，先测量再决定
4. **不设最小/最大限制** → 5 token 或 5000 token 的块都会破坏检索
5. **跨文档分块** → 绝不允许，必须先按文档分割再合并

## 10. 2026 年推荐起点

**递归 512 token、无重叠**，在 50 个查询的分层评估集（事实型 + 分析型 + 多跳型）上测量 recall@5，从那里调整。

| 场景 | 推荐策略 |
|------|---------|
| 事实型问答 | 递归 256-512 token |
| 分析型/多跳型 | 递归 512-1024 + 父子文档 |
| 大量交叉引用（合同、论文） | 后期分块或上下文检索 |
| 对话语料 | 轮次级块 + 说话者元数据 |
| 短文本（推文、评论） | 一个文档 = 一个块 |

## 补充：Late Chunking、上下文悬崖与两大翻车点深挖

> 补充日期：2026-06-17（多轮 Q&A 深化）

### A. Late Chunking 的两个关键澄清

#### A1. 整篇 token 化之后，还怎么分块？——"位置归属"≠"向量内容"

常见疑问：所有 token 都融合了全文信息，块边界不就模糊了吗？

**澄清：Transformer 是序列模型，输入 N 个 token，输出 N 个向量，位置严格一一对应。attention 只改向量的数值内容，不改 token 的位置归属。**

```text
输入位置:  [0]San  [1]Fran  [2]cisco  [3]is  [4]foggy  ... [N-1]city
经 self-attention(每个 token 看过全文)
输出向量:  v[0]   v[1]    v[2]     v[3]  v[4]    ... v[N-1]
           ↑内容融进上下文，但位置仍是第 0/4/N-1 个
```

所以分块照常——**按 token 位置索引划边界**（块1 = 位置 0-30，块2 = 位置 31-60），再对每块内的向量做 mean pool。边界是位置划的，跟向量"融合了多少信息"无关。

#### A2. 所有 token 融合了全文信息，最后输出会乱掉吗？——向量不"说人话"

这是核心误解。**检索返回给 LLM 的从来不是"从向量还原的语言"，而是原始文本。嵌入是单向、不可逆的指纹。**

存储阶段，每个 chunk 同时存两样东西：

```text
chunk 1: 向量 v1 (用于匹配) + 原文 "The city is known for its fog." (按同样边界切的原文)
```

检索阶段，向量只负责"该不该被找到"，不负责"说什么"：

```text
query "旧金山特点?" → q 跟所有 chunk 向量比相似度 → v1 命中 → 取出 v1 对应的【原文】→ 喂给 LLM
```

**LLM 永远看不到向量，也永远不从向量解码文字。** 它看到的就是原文里那句一字不差的文本。

| | 传统分块 | Late Chunking |
| --- | --- | --- |
| 给 LLM 的文本 | "The city is known for its fog." | **同一句原文**，一字不差 |
| 该句的向量 | 只见过这一句，不知道 "the city" 是谁 | token 级 attention 让它知道 "the city"=旧金山 |
| 检索 "旧金山特点" | 匹配不上（向量里没"旧金山"） | 匹配得上（向量已含"旧金山"） |

**"说什么"由原文决定（两种方法都给同一句原文，不会乱）；"能不能被检索到"由向量决定（late chunking 只让向量更准）。** "融合全文"是让每个 token 的语义表示更丰富，不是把不同句子的文字物理搅在一起。

> 比方：向量像书的索引卡（写着"第 20 页讲旧金山天气"），原文像书页本身。Late chunking 只让索引卡写得更准，但读者（LLM）最后翻开的还是第 20 页的原文，书页一个字没动。

### B. Late Chunking 在 RAG 链路中的位置：改善"中间检索环节"

```text
① 索引阶段            ② 检索阶段              ③ 生成阶段
文档→切块→存向量库      query→比相似度→选top-k    把选中块【文本】拼进prompt→LLM答
└── late chunking ──┘  └── 它让这步更准 ──┘    └── 完全不参与 ──┘
```

Late chunking 住在 ①②，**让"哪块该被召回"的判断更准（提高召回率/recall）**，不碰 ③生成阶段。它不改变最终喂给 LLM 的内容（还是原文），只提高相关块被向量相似度命中的概率。

具体修的故障：传统分块里 "The city is known for its fog." 这块向量只见过这一句，"the city" 指代谁→向量里没有"旧金山"信号→跟 "旧金山特点" 比相似度时排不进 top-k→**漏召回**。Late chunking 让该 token 向量融进"旧金山"，从而命中。课程原文 "Preserves cross-chunk context" 即此意。

### C. 上下文悬崖：发生在③生成阶段，与 late chunking 是两个环节的护栏

```text
上下文悬崖住在 ③：把检索到的块拼进 prompt 时，总量到约 2,500 token 质量急剧（非平滑）下降。
```

底层是 LLM 的 "lost in the middle"（对 prompt 中间信息注意力低）+ 召回越多噪声越多，几股力量在 ~2.5k token 叠加后质量崩塌。

| | Late Chunking | 上下文悬崖 |
| --- | --- | --- |
| 住哪个环节 | ①索引 + ②检索 | ③生成（prompt 拼装） |
| 防什么病 | **召回不足**——相关块因上下文被切断而漏掉 | **塞得过满**——top-k 太多，过 2.5k 质量崩塌 |
| 方向 | 让该进来的块**进来** | 让不该进来的块**别进来** |

一守召回率，一守 prompt 总量上限。理想 RAG = late chunking 保相关块被检索到 + 重排截断保只塞最相关少数几块、不撞悬崖。应对上下文悬崖的实操：控制送入 prompt 的总量、重排后截断、相关片段放 prompt 首尾（避开"中间被埋没"）。

### D. 翻车点一：语义分块阈值调参

"显而易见"的直觉：逐句嵌入→算相邻句余弦相似度→相似度跌破阈值处切一刀，主题最连贯，于是花精力调阈值。

翻车病根（[zh.md:32](../docs/zh.md#L32)）："有时会产生 40 token 的小片段，损害检索效果"：

1. **相似度曲线是嘈杂连续值，不是"主题开关"。** 举例、转折、引用都会造成局部低谷。阈值设高→正常低谷全被切，碎片化；设低→真主题切换漏掉。没有"对的阈值"，只有两种错误间反复横跳的值。
2. **碎片化直接砸召回率。** 40 token 块语义信号太弱，向量信息量不够，既易漏召回也易误召回。这正是 Vectara 基准里语义分块 54% 打不过递归 512 的 69% 的原因——碎片化把"主题连贯"的理论优势抵消殆尽。

更稳替代：递归分块无需调语义阈值；句子分块在 ~5k token 内接近语义效果但成本更低；真要用语义分块必须配 `min_chars`/最小 token 下限（quiz Q7）堵住碎片化。

### E. 翻车点二：重叠（overlap）收益评估

"显而易见"的直觉：相邻块共享 N token，边界处信息两块都有，避免漏掉边界内容。听着像免费保险，于是默认 10-20% 重叠（课程点名"20% 重叠"即典型直觉配置）。

翻车结论（[zh.md:19](../docs/zh.md#L19)）：SPLADE + Mistral-8B 在 Natural Questions 上"重叠没有带来任何可衡量的收益"：

1. **边界信息并非丢失，只是被分到相邻块。** 一句被切到 A 块结尾 + B 块开头，信息没消失。重叠只是让这句在 A、B 都完整放一遍。但只要 A 或 B 任一块被召回信息就进 prompt 了——重复放并不能让"本来检索不到的块"变得可检索，对召回率几乎零贡献。
2. **代价实打实：索引体积膨胀。** 20% 重叠 = 每块 1/5 内容与邻居重复，存大量冗余向量，存储和检索成本显著上升，收益却测不到。纯亏买卖。

### F. 收束原则：分块的"智能程度"与"效果"不成正比

两大翻车点共享同一陷阱——**把连续、嘈杂、本无硬边界的现实（主题渐变、句子边界归属）当成能用一个旋钮"切干净"的东西**：

- 语义分块假设"主题有清晰阈值切分点" → 实际嘈杂 → 碎片化 → 砸召回。
- 重叠假设"边界信息会丢失" → 实际只分到邻居块 → 无收益 → 白增存储。

递归分块之所以成为 2026 默认，恰恰因为它**不假装能智能识别主题**，只尊重文档原有结构符号优雅回退，少几个会爆炸的旋钮反而更稳。

> **元教训**：每多一个需调的旋钮（语义阈值、重叠比例），就多一个翻车点。先用朴素递归分块跑基线，再用基准证明的收益决定要不要上更复杂策略——别用听起来合理的配置去赌。"显而易见的答案（语义分块 + 20% 重叠 + 1000 token）通常是错误的。"
