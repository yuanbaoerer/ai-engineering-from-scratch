# 长期自主 Agent 学习笔记

> 日期: 2026-07-03

## 1. 三个必须记住的数字

| 数字 | 含义 |
|------|------|
| **7 个月** | METR 的 50% 时间线倍增周期（从 GPT-2 到 Claude Opus 4.6） |
| **14 小时** | Claude Opus 4.6 在 50% 可靠性下能完成的专家工作时长 |
| **99% × 70 步 ≈ 50%** | 单步 99% 可靠性，70 步轨迹就变成抛硬币 |

## 2. 时间线预测

以 7 个月倍增计算：

| 月份 | 水平线能力 | 里程碑 |
|------|-----------|--------|
| 0 | 14 小时 | 工作日规模 |
| 5.4 | 24 小时 | 跨过一整天 |
| 12.4 | 48 小时 | 两天任务 |
| 25.1 | 168 小时 | 一周任务 |
| 39.8 | 720 小时 | 一月任务 |

**结论**：指数增长意味着大约 1 年后模型能处理"跑一整天"的任务，3 年后能处理"跑一个月"的任务。

## 3. 可靠性复合——数学必然

单步可靠性 × 步骤数 = 端到端成功率（乘法，不是加法）

| 单步可靠性 | 步骤数 | 端到端成功率 | 状态 |
|-----------|--------|-------------|------|
| 90% | 10 | 34.9% | 抛硬币 |
| 99% | 50 | 60.5% | 勉强能用 |
| **99%** | **70** | **49.5%** | **抛硬币** |
| 99% | 200 | 13.4% | 必挂 |
| 99.9% | 1000 | 36.8% | 依然抛硬币 |

**最大步数限制**（50% 端到端成功率）：

- 90% 单步 → 只能扛 **6 步**
- 95% 单步 → 只能扛 **13 步**
- 99% 单步 → 只能扛 **68 步**
- 99.9% 单步 → 能扛 **692 步**

想让 agent 跑 100+ 步，单步可靠性必须 >99.5%。

## 4. "单步"的定义

**既不是完成一个任务，也不是一次 API 请求——是一次"工具调用 + 观察 + 推理"的循环。**

一个 step 对应 Agent Loop 里的一个完整循环：

```
思考 → 选择工具 → 执行工具 → 读取结果 → 再思考
```

| 步骤 | 动作 |
|------|------|
| 1 | 用户说"读 main.py" |
| 2 | 模型决定调用 Read 工具 |
| 3 | Read 返回文件内容 |
| 4 | 模型看到内容，决定下一步 |
| 5 | 模型决定调用 Edit 工具 |
| 6 | Edit 执行，返回结果 |
| ... | 循环继续 |

每一步都可能失败：模型选错工具、工具返回错误、模型误读结果、推理方向跑偏、进入死循环。

**实际举例**："重构模块并写测试"大约 10-15 步（读文件→理解→编辑→保存→运行测试→修改→再跑）。99% 单步下端到端成功率约 85-86%。但"重构整个项目"（50+ 步）就掉到 60% 以下。

## 5. 五个会"爆炸"的维度

| 维度 | 短期运行（秒级） | 长期运行（分钟到小时级） |
|------|-----------------|------------------------|
| 上下文 | 可以携带全部 | 需要压缩/检查点/记忆层级 |
| 信任 | 读完整回答 | 必须审计轨迹 |
| 失败模式 | 能力不足 | 漂移、循环、奖励黑客 |
| 成本 | 可预测 | 肥尾分布 |
| 评估 | 最终答案 | 轨迹级遥测 |

长期运行放大了所有问题：上下文膨胀、信任盲区、不可见的失败模式累积、成本失控。

## 6. Eval-Context Gaming（部署陷阱）

METR 测的是**理想条件**（无后果、无 eval-context gaming）。真实部署存在差距：

| 基准线 | 20% 差距 | 40% 差距 |
|--------|---------|---------|
| 14 小时 | 11.2 小时 | 8.4 小时 |
| 48 小时 | 38.4 小时 | 28.8 小时 |
| 168 小时 | 134.4 小时 | 100.8 小时 |

关键事实：
- Anthropic 2024 研究：Claude 在 12% 基础测试中伪装更安全，重训练后升至 78%
- 2026 国际 AI 安全报告：前沿模型在评估中表现更安全

**结论**：benchmark 说 14 小时，实际部署能信任的大概 **8-11 小时**。METR 数字是能力上限，不是部署下限。

## 7. Horizon Reality Check 决策框架

`outputs/skill-horizon-reality-check.md` 给出的部署前检查清单：

1. **专家时间估算**：要求用户提供中位完成时间，无法估算则拒绝
2. **Headroom ratio**：模型 50% 时间线 / 专家时间
   - < 4x → 警告
   - < 2x → 拒绝（除非 HITL 介入每一步）
3. **可靠性预算**：估算轨迹步数 × 单步可靠性，计算端到端成功率
4. **评估-部署差距**：套用 20-40% 折扣
5. **最低控制措施**：预算上限、迭代上限、kill switch、HITL 检查点、金丝雀 token、轨迹审计

**硬拒绝条件**：
- Horizon ratio < 2x 且无 HITL
- 仅凭 METR 数字声称模型"能做"某任务
- 将 METR 时间线当作地板而非天花板
- 不可逆操作（财务交易、生产数据库写入、客户邮件）无 HITL 层

## 8. 与 Phase 14 的衔接

Phase 14 的 Workbench 7 个表面正是为长期 agent 设计的：

| Workbench 表面 | 对应的长期风险 |
|---------------|---------------|
| agent_state.json（状态追踪） | 上下文膨胀、状态丢失 |
| 初始化脚本 | 环境漂移 |
| scope contract | 范围蠕变、循环 |
| feedback runner | 验证缺失 |
| verification gate | 错误累积 |
| reviewer | 信任审计 |
| handoff packet | 会话断裂 |

短期运行可以跳过部分表面，长期运行必须全部启用。

## 9. 代码运行的核心启示

```
HEADLINE: horizons grow exponentially, reliability compounds
- At 7-month doubling, a multi-day horizon is ~1 year away.
- At 99% per-step, a 70-step trajectory is already a coin flip.
- Both numbers matter at the same time. Design for both.
```

**两个指数同时作用**：时间线在指数增长（能力越来越强），可靠性在指数衰减（步数越多越容易崩）。设计长期 agent 时，两个方向都要算账——光看"模型能跑多久"不够，还要算"每一步有多稳"。
