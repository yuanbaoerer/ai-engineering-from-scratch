# 动作预算、迭代上限与成本治理器

> 一家中型电商的代理在团队启用"订单追踪"技能后，月度 LLM 成本从 1,200 美元跳到了 4,800 美元。这不是定价错误。这是一个代理发现了一个新的循环并在其中持续花费。微软的 Agent Governance Toolkit（2026 年 4 月 2 日）将针对这类问题的防御编纂为：每次请求的 `max_tokens`、每任务 token 和美元预算、每日/每月上限、迭代上限、分层模型路由、提示缓存、上下文窗口化、昂贵动作的人类在环（HITL）检查点、预算突破时的急停开关。Anthropic 的 Claude Code Agent SDK 以不同的名称发布了相同的原语。财务速率限制——例如 10 分钟内花费超过 50 美元就切断访问——比月度上限更快地捕获循环。

**类型：** 学习
**语言：** Python（标准库，分层成本治理器模拟器）
**前置条件：** 第 15 阶段 · 10（权限模式），第 15 阶段 · 12（持久执行）
**时间：** ~60 分钟

## 问题

自主代理在每一轮都花费真金白银。聊天机器人的坏输出是一个坏回复；代理的坏循环是一张账单。业界记录的这种故障模式术语是"钱包拒绝服务"（Denial of Wallet）——代理持续推理、持续调用工具、持续计费，而没有任何东西阻止它，因为根本没有什么是为此设计的。

修复方案不是一个数字。它是一个在不同时间尺度和粒度上的限制栈：每次请求、每任务、每小时、每日、每月。一个设计良好的栈能在几分钟内捕获失控循环，几小时内捕获缓慢泄漏，一天内捕获糟糕的发布。同样的栈在代理是长时域且自主的时候保持预算不超支。

这是一堂工程课：数学很简单，纪律才是团队失败的地方。下面的限制列表在微软 Agent Governance Toolkit 或 Anthropic Claude Code Agent SDK 文档中都有命名。

## 概念

### 成本治理器栈

1. **每次请求的 `max_tokens`。** 简单。防止单次调用生成无界的补全内容。
2. **每任务 token 预算。** 整个运行不超过 N 个 token。达到上限时硬停止。
3. **每任务美元预算。** 与 token 相同，但以货币计。Claude Code 中的 `max_budget_usd`。
4. **每工具调用上限。** 不超过 N 次 `WebFetch` 调用、N 次 `shell_exec` 调用等。
5. **迭代上限（`max_turns`）。** 代理循环总迭代次数；防止无限推理循环。
6. **每分钟/每小时/每日/每月上限。** 滑动窗口。在不同时间尺度捕获泄漏。
7. **财务速率限制。** 例如"如果 10 分钟内花费超过 50 美元，切断访问。"在月度上限触发前捕获基于循环的消耗。
8. **分层模型路由。** 默认使用较小模型；仅当分类器判断任务需要时才升级到较大模型。
9. **提示缓存。** 系统提示和稳定上下文存储在提供商缓存中；重新发送的 token 成本接近零。
10. **上下文窗口化。** 压缩/摘要以保持活跃上下文低于阈值；直接降低 token 成本。
11. **昂贵动作的 HITL 检查点。** 在已知昂贵的动作（长工具调用、大下载、昂贵的模型升级）之前，需要人类确认。
12. **预算突破时的急停开关。** 任何上限触发时会话中止。上限被记录；需要单独的重新启用路径。

### 为什么需要栈而非单一上限

单一月度上限只有在钱包花光后才能捕获失控代理。单一每次请求上限在会话层面什么也捕获不到。不同的故障模式需要不同的时间尺度：

- **失控循环**（代理卡在 5 秒重试中）：被速率限制捕获。
- **缓慢泄漏**（代理每任务完成约 2 倍预期工作量）：被每日上限捕获。
- **糟糕的发布**（新版本使用 5 倍 token）：被每周/每月上限捕获。
- **合理激增**（真实需求，非 bug）：被小时/日上限捕获，有清晰日志。

### Claude Code 的预算表面

Claude Code Agent SDK 公开以下内容（公开文档）：

- `max_turns` — 迭代上限。
- `max_budget_usd` — 美元上限；突破时会话中止。
- `allowed_tools` / `disallowed_tools` — 工具白名单和黑名单。
- 工具使用前的钩子点，用于自定义成本核算。

与权限模式阶梯（第 10 课）结合使用。没有 `max_budget_usd` 的 `autoMode` 会话是无治理的自主。Anthropic 明确将 Auto Mode 定位为需要预算控制；分类器与成本是正交的。

### EU AI Act、OWASP Agentic Top 10

微软的 Agent Governance Toolkit 涵盖 OWASP Agentic Top 10 和 EU AI Act 第 14 条（人类监督）要求。在欧盟生产环境中，日志记录和上限执行不是可选的。

### 观测到的 1,200 → 4,800 美元案例

微软文档中的真实案例：一个电商代理在添加新工具后月度成本翻了三倍。该工具允许代理在每次会话期间轮询订单状态。没有循环检测。没有每工具上限。没有周环比增长告警。修复方案是每工具上限加每日增长告警。这是一个模板：每个新的工具表面都是一个新的潜在循环；每个新工具都需要自己的上限和自己的告警。

## 使用它

`code/main.py` 模拟有和没有分层成本治理器栈的代理运行。模拟代理在若干轮后漂移进入轮询循环；分层栈在速率窗口内捕获它，而单一月度上限要到几天后才会触发。

## 交付它

`outputs/skill-agent-budget-audit.md` 审计拟议代理部署的成本治理器栈并标记缺失的层。

## 练习

1. 运行 `code/main.py`。确认在轮询循环轨迹上速率限制在迭代上限之前触发。现在禁用速率限制，测量代理在迭代上限捕获它之前"花费"了多少。

2. 为浏览器代理（第 11 课）设计一组每工具上限。哪个工具需要最严格的上限？哪个工具可以无限制运行而无风险？

3. 阅读微软 Agent Governance Toolkit 文档。列出工具包命名的每种上限类型。将每个映射到一种故障模式（失控循环、缓慢泄漏、糟糕的发布、激增）。

4. 为一个现实任务（例如"在一个仓库中分类 50 个 issue"）估算一夜无人值守运行的成本。将 `max_budget_usd` 设为你的点估计的 2 倍。证明 2 倍的合理性。

5. Claude Code 的 `max_budget_usd` 基于会话累计成本触发。设计一个你会在外部执行的互补速率限制。什么触发切断？重新启用是什么样的？

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|---|---|---|
| 钱包拒绝服务 | "失控账单" | 代理循环产生花费而没有上限阻止 |
| max_tokens | "每次请求上限" | 单次补全内容大小的上限 |
| max_turns | "迭代上限" | 会话中代理循环迭代次数的上限 |
| max_budget_usd | "美元急停开关" | 会话成本上限；突破时中止 |
| 速率限制 | "速率上限" | 短窗口内的花费限制（如 50 美元/10 分钟） |
| 分层路由 | "先用小模型" | 默认使用廉价模型；仅当分类器判断时才升级 |
| 提示缓存 | "缓存系统提示" | 提供商侧缓存将重新发送的 token 成本降至接近零 |
| HITL 检查点 | "人类审批门" | 昂贵动作前需要人类确认 |
