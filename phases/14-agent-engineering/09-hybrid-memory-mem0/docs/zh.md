# 混合记忆：向量 + 图 + KV（Mem0）

> Mem0（Chhikara 等，2025）将记忆视为三个并行存储——向量用于语义相似性，KV 用于快速事实查找，图用于实体关系推理。一个评分层在检索时融合三者的结果。这是 2026 年生产环境中外部记忆的标准方案。

**类型：** 构建
**语言：** Python（标准库）
**前置条件：** 第 14 阶段 · 07（MemGPT），第 14 阶段 · 08（Letta Blocks）
**时间：** 约 75 分钟

## 学习目标

- 解释为什么单一存储（仅向量、仅图、仅 KV）不足以满足智能体记忆的需求。
- 列出 Mem0 的三种并行存储以及各自的优化目标。
- 描述 Mem0 的融合评分——相关性、重要性、时效性——以及为什么它是加权求和而非层级结构。
- 使用标准库实现一个玩具级三存储记忆系统，包含写入所有三个存储的 `add()` 和融合结果的 `search()`。

## 问题

对于三类查询，单一存储总有一类处理不好：

- **语义相似性** —— "我们上周讨论了智能体漂移的什么内容？" 向量存储占优；KV 和图存储无法胜任。
- **事实查找** —— "用户的电话号码是什么？" KV 存储占优；向量存储浪费资源，图存储大材小用。
- **关系推理** —— "哪些客户共享同一个计费实体？" 图存储占优；向量和 KV 无法回答。

生产级智能体在一个会话中会发起所有三类查询。单一存储对其中两类总是力不从心。Mem0 的贡献在于将三者统一在单一的 `add`/`search` 接口背后，并通过融合评分函数将结果整合。

## 概念

### 三种并行存储

Mem0（arXiv:2504.19413，2025 年 4 月）执行 `add(text, user_id, metadata)` 时：

1. 从文本中提取候选事实（由 LLM 驱动）。
2. 将每条事实写入向量存储（嵌入），用于语义搜索。
3. 将每条事实写入 KV 存储，以 (user_id, fact_type, entity) 为键，实现 O(1) 查找。
4. 将每条事实写入图存储（Mem0g），作为类型化边，用于关系查询。

执行 `search(query, user_id)` 时：

1. 向量存储通过嵌入余弦相似度返回 top-k 结果。
2. KV 存储通过查询派生的 (user_id, type, entity) 键返回精确匹配结果。
3. 图存储返回从查询实体可达的子图。
4. 一个评分层融合三者的结果。

### 融合评分

```
score = w_relevance * relevance(q, record)
      + w_importance * importance(record)
      + w_recency * recency(record)
```

- **相关性** —— 向量余弦相似度、KV 精确匹配、图路径权重。
- **重要性** —— 在写入时标记或通过学习得出（某些事实更重要：姓名、ID、策略）。
- **时效性** —— 基于上次写入或读取后的指数衰减。

权重根据产品进行调优。聊天智能体提高 `w_recency`；合规智能体检高 `w_importance`；检索智能体提高 `w_relevance`。

### Mem0g 与时序推理

Mem0g 增加了冲突检测器。当新事实与现有边矛盾时，现有边被标记为无效但不删除。时序查询（"用户三月时所在的城市是哪里？"）遍历在该时间点有效的子图。

这是 Letta 无效化模式的通用化，达到合规级别。

### 基准测试数据

Mem0 论文报告（2025）：

- **LoCoMo**（长对话记忆）：91.6
- **LongMemEval**（长期情景记忆）：93.4
- **BEAM 1M**（百万 token 记忆基准）：64.1

对比基线（全上下文 128k LLM、扁平向量存储、扁平 KV）均低 10 分以上。基准测试并不能完全证明选择的正确性——还需考量实际运行形态——但这些数字表明融合设计并非四舍五入的误差。

### 范围分类

Mem0 按范围划分记忆：

- **用户记忆** —— 跨会话持久化，以 `user_id` 为键。
- **会话记忆** —— 在单一线程内持久化。
- **智能体记忆** —— 每个智能体实例的状态。

每次写入选择一个范围。检索可以跨范围查询，并为每个范围设置权重。不加区分地混用范围就是"助手把 Bob 的项目信息告诉了 Alice"这类事故的根源。

### 常见问题

- **嵌入漂移。** 向量结果在前一百次查询时看起来正确，但随着语料增长而退化。定期对 top-N 高频使用的记录重新嵌入。
- **KV 模式蔓延。** `(user_id, type, entity)` 看起来简单，直到每个团队都添加自己的 `type`。每季度审计一次类型集合。
- **图爆炸。** 一个嘈杂的提取器每条消息增加 50 条边。限制每次 `add` 调用的图写入数量；丢弃低置信度的边。

## 构建

`code/main.py` 使用标准库实现三存储模式：

- `VectorStore` —— 用朴素的 token 重叠相似度模拟嵌入。
- `KVStore` —— 以 `(user_id, fact_type, entity)` 为键的字典。
- `GraphStore` —— 类型化边（subject, relation, object, valid）。
- `Mem0` —— 顶层门面，包含 `add()`、`search()`、融合评分和范围感知检索。
- 一个多用户、多会话对话的完整示例。

运行方式：

```
python3 code/main.py
```

输出会展示三条独立的召回路径以及融合后的 top-k 结果。在 `main()` 顶部调整评分权重，观察排名的变化。

## 使用

- **Mem0（Apache 2.0）** —— 生产就绪。可使用 Postgres + Qdrant + Neo4j 自行部署，或使用托管云服务。
- **Letta** —— 三层架构：core/recall/archival；自带向量和图存储后端。
- **Zep** —— 商业替代方案，支持时序知识图谱和事实提取。
- **自建方案** —— 当需要精确控制提取器（合规场景）或融合权重（时效性为主导的语音智能体）时。

## 交付

`outputs/skill-hybrid-memory.md` 生成一个三存储记忆脚手架，内置融合评分器、范围分类和时序无效化机制。

## 练习

1. 将玩具向量相似度替换为真实的嵌入模型（sentence-transformers、Ollama、OpenAI embeddings）。在合成的长对话上测量 recall@10。排名在 1000 次写入后是否会漂移？
2. 添加时序查询：`search(query, as_of=timestamp)`。仅返回在该时间点或之前有效的记录。哪个存储需要最多的工作？
3. 实现冲突检测器：如果传入事实与图边矛盾，将旧边标记为无效并记录两条。在"用户住在柏林" -> "用户住在里斯本"上测试。
4. 扩展融合评分器，增加 `user_feedback` 维度（对检索记录点踩/点赞）。如何防止博弈（智能体只返回它已经喜欢的记录）？
5. 阅读 Mem0 文档（`docs.mem0.ai`）。将玩具系统移植为 `mem0` 客户端调用。在相同的 20 个测试查询上比较检索质量。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|---------|---------|
| 混合记忆 | "向量加图加 KV" | 三种存储并行写入，检索时融合 |
| 事实提取 | "记忆摄取" | LLM 将文本拆解为 (entity, relation, fact) 元组的步骤 |
| 融合评分 | "相关性排序" | 相关性、重要性、时效性的加权求和 |
| 范围 | "记忆命名空间" | user / session / agent——决定谁能看到什么 |
| Mem0g | "记忆图" | 带时序有效性的类型化边，用于关系查询 |
| 时序无效化 | "软删除" | 将矛盾的边标记为无效；永不删除 |
| 嵌入漂移 | "检索退化" | 随着语料增长，向量质量退化；需定期重新嵌入 |
