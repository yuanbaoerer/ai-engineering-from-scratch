# 工具使用与函数调用

> Toolformer (Schick et al., 2023) 开创了自监督工具标注方法。Berkeley Function Calling Leaderboard V4 (Patil et al., 2025) 设定了 2026 年的评估基准：40% 智能体场景，30% 多轮对话，10% 实时场景，10% 非实时场景，10% 幻觉检测。单轮调用已基本解决。记忆、动态决策和长链工具调用仍是开放问题。

**类型：** 构建
**语言：** Python（标准库）
**前置课程：** 第 14 阶段 · 01（智能体循环），第 13 阶段 · 01（函数调用深入解析）
**时间：** ~60 分钟

## 学习目标

- 阐述 Toolformer 的自监督训练信号：仅在执行工具能降低下一个 token 损失时保留工具标注。
- 说出 BFCL V4 的五个评估类别及其各自的评估内容。
- 实现一个基于标准库的工具注册表，包含 schema 验证、参数强制转换和执行沙箱。
- 诊断 2026 年的三个开放问题：长链工具调用、动态决策和记忆。

## 问题背景

早期的工具使用关注的是：模型能否预测出正确的函数调用？而现代工具使用关注的是：模型能否在 40 步的调用链中串联工具，同时具备记忆能力、部分可观测性、从工具故障中恢复的能力，并且不幻觉出不存在的工具？

Toolformer 建立了基线：模型可以通过自监督学习判断何时调用工具。BFCL V4 定义了 2026 年的评估目标。两者之间的差距正是生产级智能体所处的空间。

## 核心概念

### Toolformer (Schick et al., NeurIPS 2023)

核心思想：让模型用自己的预训练语料库标注候选 API 调用。对每个候选调用执行实际操作。只有当包含工具调用结果能降低下一个 token 的损失时，才保留该标注。然后在过滤后的语料库上进行微调。

涵盖的工具包括：计算器、问答系统、搜索引擎、翻译器、日历。自监督信号完全基于工具是否有助于预测文本——无需人工标签。

规模效应：工具使用能力在规模扩大时涌现。较小的模型会因工具标注而受损；较大的模型则受益。这就是为什么 2026 年的前沿模型内置了强大的工具使用能力，而大多数 7B 模型需要显式的工具使用微调才能可靠工作。

### Berkeley Function Calling Leaderboard V4 (Patil et al., ICML 2025)

BFCL 是 2026 年的事实标准评估基准。V4 的组成如下：

- **智能体场景（40%）** — 完整的智能体轨迹：记忆、多轮对话、动态决策。
- **多轮对话（30%）** — 带工具调用链的交互式对话。
- **实时场景（10%）** — 用户提交的真实提示（更难的分布）。
- **非实时场景（10%）** — 合成测试用例。
- **幻觉检测（10%）** — 检测何时不应调用任何工具。

V3 引入了基于状态的评估：在工具调用序列之后，检查 API 的实际状态（例如"文件是否已创建？"），而非匹配工具调用的 AST。V4 新增了网页搜索、记忆和格式敏感性类别。

2026 年的关键发现：单轮函数调用已接近解决。失败主要集中在记忆（跨轮次传递上下文）、动态决策（基于先前结果选择工具）、长链调用（20 步以后出现漂移）和幻觉检测（在没有合适工具时拒绝调用）。

### 工具 Schema

每个提供商都有自己的 schema。细节各有不同，但基本结构一致：

```
name: string
description: string (功能说明、使用场景)
input_schema: JSON Schema (properties, required, types, enums)
```

Anthropic 直接使用 `input_schema`。OpenAI 使用 `function.parameters`。两者都接受 JSON Schema。描述至关重要——模型依赖描述来选择正确的工具。糟糕的工具描述是选错工具的首要原因。

### 参数验证

不要信任任何工具调用。必须验证：

1. **类型强制转换。** 模型可能在 schema 要求 int 时返回字符串 "5"。如果语义明确则强制转换；否则拒绝。
2. **枚举验证。** 如果 schema 规定 `status in {"open", "closed"}` 而模型输出了 `"in_progress"`，则返回描述性错误并拒绝。
3. **必填字段。** 缺少必填字段 → 立即返回错误观察给模型，而非崩溃。
4. **格式验证。** 日期、邮箱、URL — 使用具体的解析器验证，而非正则表达式。

每次验证失败都应返回结构化的观察结果，以便模型能用正确的格式重试。

### 并行工具调用

现代提供商支持在单个助手轮次中并行调用多个工具。流程如下：

1. 模型发出 3 个工具调用，各自带有不同的 `tool_use_id`。
2. 运行时执行这些调用（如果相互独立则并行执行）。
3. 每个结果通过 `tool_use_id` 关联，作为 `tool_result` 块返回。

工程规则：将关联 ID 视为关键字段。交换它们会导致工具与结果的错误匹配。

### 沙箱

工具执行是沙箱的边界。详见第 09 课。简要说明：每个工具应指定读写范围、网络访问、超时时间和内存限制。通用的 `run_shell(cmd)` 是危险信号；特定的 `git_status()` 更安全。

## 实际应用

每个提供商都有自己的工具 schema — Anthropic、OpenAI、Gemini、Bedrock。如果需要多提供商兼容，可使用转换层（OpenAI Agents SDK、Vercel AI SDK、LangChain tool adapter）。BFCL 是参考基准——如果工具使用是产品的核心功能，发布前请用它来测试你的智能体。

## 练习

1. 添加一个"无操作"工具，让模型显式拒绝使用任何其他工具。在类似 BFCL 的幻觉测试上进行测量。
2. 实现 int-as-string 和 float-as-string 的参数强制转换。强制转换从哪里开始掩盖真正的 bug？
3. 添加每个工具的超时和熔断器（连续失败 3 次后拒绝该工具 60 秒）。这如何改变模型的恢复行为？

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|---------|---------|
| 函数调用 | "工具使用" | 带验证 schema 的结构化输出工具调用 |
| Toolformer | "自监督工具标注" | Schick 2023 — 保留那些结果能降低下一个 token 损失的工具调用 |
| BFCL | "Berkeley Function Calling Leaderboard" | 2026 年基准：40% 智能体场景，30% 多轮对话，10% 实时场景，10% 非实时场景，10% 幻觉检测 |
