# Anthropic 的工作流模式：简单优于复杂

> Schluntz 和 Zhang（Anthropic，2024年12月）区分了工作流（预定义路径）和智能体（动态工具使用）。五种工作流模式涵盖了大多数场景。首先使用直接 API 调用。仅当步骤无法预测时才添加智能体。

**类型：** 学习 + 构建
**语言：** Python（标准库）
**先决条件：** 第14阶段 · 01（智能体循环）
**时间：** 约60分钟

## 学习目标

- 说出 Anthropic 的五种工作流模式：提示链、路由、并行化、编排器-工作者、评估器-优化器。
- 解释智能体与工作流的区别以及各自的工程成本。
- 识别何时选择工作流而非智能体（反之亦然）。
- 使用标准库针对脚本化 LLM 实现所有五种模式。

## 问题所在

团队为了只需要单次函数调用的问题而采用多智能体框架。成本是真实的：框架添加的层次掩盖了提示、隐藏了控制流，并引发了过早的复杂性。Schluntz 和 Zhang 于2024年12月发布的文章是业界最常被引用的反驳：从简单开始，仅在证明其成本合理时才添加复杂性。

## 概念

### 工作流与智能体

- **工作流。** 通过预定义代码路径编排 LLM 和工具。工程师拥有图。
- **智能体。** LLM 动态指导自己的工具并采取自己的步骤。模型拥有图。

两者各有其用。工作流更便宜、更快、更容易调试。智能体解锁开放式问题，但使故障模式更难推理。

### 增强型 LLM

所有五种模式的基础：一个集成了三种能力的 LLM —— 搜索（检索）、工具（操作）、记忆（持久化）。任何 API 调用都可以使用这些能力。

### 五种模式

1. **提示链。** 调用1的输出是调用2的输入。当任务具有清晰的线性分解时使用。步骤之间可选择性地设置程序化门控。

2. **路由。** 分类器 LLM 选择调用哪个下游 LLM 或工具。当不同类别的输入需要不同的处理方式时使用（一级支持 vs 退款 vs 缺陷 vs 销售）。

3. **并行化。** 同时运行 N 个 LLM 调用，汇总结果。两种形式：分段（不同部分）和投票（相同提示，N 次运行，多数/综合）。

4. **编排器-工作者。** 编排器 LLM 动态决定运行哪些工作者（也是 LLM）并综合它们的输出。类似于智能体循环，但编排器不会无限循环。

5. **评估器-优化器。** 一个 LLM 提出答案，另一个 LLM 评估它。迭代直到评估器通过。这是 Self-Refine（第05课）的泛化。

### 工作流优于智能体的场景

- **可预测的任务。** 如果你可以列举步骤，你就应该这样做。
- **成本受限的任务。** 工作流具有有界的步骤数；智能体可能失控。
- **合规性受限的任务。** 审计人员想要读取图，而不是从轨迹中推断。

### 智能体优于工作流的场景

- **开放式研究。** 当下一步取决于上一步返回的结果时。
- **可变长度任务。** 从几分钟到几小时的工作，步骤数未知。
- **新领域。** 当你还不知道正确的工作流时 —— 先探索，再固化。

### 上下文工程的伙伴

"AI 智能体的有效上下文工程"（Anthropic 2025）形式化了相邻学科：200k 窗口是预算，而不是容器。包含什么、何时压缩、何时让上下文增长。在本课程的第14阶段上下文压缩课程中（本课程中重新编号之前的第14阶段早期第06课）有详细介绍。

## 构建它

`code/main.py` 针对 `ScriptedLLM` 实现了所有五种工作流模式：

- `prompt_chain(input, steps)` —— 顺序执行。
- `route(input, classifier, handlers)` —— 分类 + 分派。
- `parallel_vote(prompt, n, aggregator)` —— N 次运行，汇总。
- `orchestrator_workers(task, workers)` —— 编排器选择工作者。
- `evaluator_optimizer(task, proposer, evaluator, max_iter)` —— 循环直到通过。

运行它：

```
python3 code/main.py
```

每种模式打印其跟踪信息。每种模式的总代码行数约为10-15行；框架的成本以千行代码计算。

## 使用它

- 大多数任务使用直接 API 调用。
- 仅在模式确实需要持久状态（LangGraph）、actor 模型并发（AutoGen v0.4）或角色模板（CrewAI）时才使用框架。
- 当你想要 Claude Code 的工具链形状而不想重建它时，可以使用 Claude Agent SDK。

## 交付它

`outputs/skill-workflow-picker.md` 为给定的任务描述选择合适的模式，包括决策理由以及当工作流不足时重构为智能体的路径。

## 练习

1. 实现具有置信度阈值的路由。低于阈值 -> 升级给人工处理。对于一级支持用例，阈值应该设在哪里？
2. 为 `parallel_vote` 添加超时。当一个调用挂起时会发生什么？如何汇总缺失的投票？
3. 将 `evaluator_optimizer` 变成一个老虎机：在迭代中保留前2个输出，这样后期的好结果不会被后期的坏结果覆盖。
4. 结合提示链和路由：路由器从三个链中选择一个。衡量与单个大提示替代方案的令牌成本对比。
5. 选择你的一项生产功能。绘制工作流图。计算步骤。智能体在这里真的会更好吗？

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|----------|
| 工作流 | "预定义流程" | 工程师拥有的 LLM 和工具调用图 |
| 智能体 | "自主 AI" | 模型拥有的图；动态工具指导 |
| 增强型 LLM | "带工具的 LLM" | LLM + 搜索 + 工具 + 记忆；原子单元 |
| 提示链 | "顺序调用" | 调用 N 的输出是调用 N+1 的输入 |
| 路由 | "分类器分派" | 选择哪个链/模型处理输入 |
| 并行化 | "扇出" | N 个并发调用；通过分段或投票汇总 |
| 编排器-工作者 | "分派器智能体" | 编排器 LLM 动态选择专家 LLM |
| 评估器-优化器 | "提案者 + 评委" | 迭代直到评估器通过；Self-Refine 泛化 |
