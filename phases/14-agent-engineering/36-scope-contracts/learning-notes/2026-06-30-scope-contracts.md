# 范围契约与任务边界学习笔记

> 日期: 2026-06-30

## 1. 核心问题：范围蔓延 (Scope Creep)

Agent 在执行任务时，容易超出预定范围修改文件。例如“修复登录bug”可能连带修改邮件助手、数据库驱动、README等。每个改动当时看似合理，但整体构成了与审查时不同的变更。这种“范围蔓延”是最被低估的失败模式，因为 Agent 每一步都在“合理解释”，但总和已偏离任务。

## 2. 解决方案：范围契约 (Scope Contract)

为每个任务创建一个 `scope_contract.json` 文件，明确任务边界。契约在任务开始时被 Agent 读取，在任务结束时被验证器检查。它将“保持在范围内”从愿望变为可检查的约束。

## 3. 契约字段详解

| 字段 | 作用 |
|------|------|
| `task_id` | 关联任务看板 |
| `goal` | 一句话目标，可供审查者验证 |
| `allowed_files` | 允许修改的文件（glob模式） |
| `forbidden_files` | 禁止修改的文件（负空间，是契约的一半） |
| `acceptance_criteria` | 测试命令或断言，证明任务完成 |
| `rollback_plan` | 一段回滚操作指南 |
| `approvals_required` | 需要人工审批的操作 |

**关键点**：没有 `forbidden_files` 的契约是不完整的。负空间（禁止什么）与正空间（允许什么）同等重要。

## 4. Glob 模式 vs 原始路径

使用 glob 模式（如 `app/**/*.py`）而非硬编码路径，因为真实仓库会移动文件。Glob 模式在重构后仍能保持契约有效。

## 5. 范围检查机制

1. Agent 运行后产生 diff（修改的文件列表）。
2. 检查器读取 diff、契约中的允许/禁止 glob、以及验收命令的运行结果。
3. 对比每个修改的文件是否在允许范围内、是否触碰禁止范围。
4. 输出违规列表（violations）、范围内文件（in_scope）、越界文件（off_scope）。
5. 验证门（verification gate）可根据违规情况决定是否阻止。

## 6. 生产环境模式

- **违规预算 (Violation Budget)**：允许轻微越界作为警告，仅当超出预算时才阻止合并。这是门控系统能日常使用与被禁用的关键区别。
- **严重性不对称**：修改 `docs/` 通常为警告，修改 `scripts/`、`migrations/`、`config/prod/` 则阻止。这种不对称应在契约中明确定义。
- **时间与网络预算**：添加 `time_budget_minutes` 限制运行时长，`network_egress` 限制外部访问。它们是文件 glob 之外的必要维度。
- **specsmaxxing 实践**：在调用 Agent 前用 YAML 编写范围契约，可将 rabbit-hole 率从 52% 降至 21%，且无需改变 Agent 模型。

## 7. 多契约合并语义（最小权限原则）

当多个契约同时适用时（如项目级契约 + 任务级契约），合并规则为：
- `allowed_files`：取交集（两个契约都允许才行）
- `forbidden_files`：取并集（任一契约禁止即禁止）
- `time_budget_minutes`：取最小值（最严格限制）
- `approvals_required`：累加
- `network_egress`：`None` 遵循另一方，两个列表取交集，`deny-all` 保留

## 8. 关键洞察

- **契约即检查**：范围契约使范围蔓延变得可见、自动、可审查。
- **负空间是半壁江山**：明确禁止什么与允许什么同等重要。
- **Glob 抵抗重构**：使用模式匹配而非硬编码路径，契约才能持久。
- **预算制优于二元制**：违规预算让门控系统在实际工作中可用，而非被团队禁用。
- **范围是多维的**：文件、时间、网络访问都是范围维度，需要同时约束。
