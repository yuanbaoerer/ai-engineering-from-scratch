# 使用 HTN 和进化搜索进行规划

> 符号规划处理那些计划可证明正确的情况。进化代码搜索处理那些适应度函数可机器检查的情况。ChatHTN（2025）和 AlphaEvolve（2025）展示了当与 LLM 结合时各自能解锁什么能力。

**类型：** 构建
**语言：** Python（标准库）
**前置课程：** 第 14 阶段 · 02（ReWOO 和规划与执行）
**时间：** ~75 分钟

## 学习目标

- 解释层次任务网络：任务、方法、算子、前置条件、效果。
- 描述 ChatHTN 的混合循环——符号搜索与 LLM 回退分解。
- 解释 AlphaEvolve 的进化循环以及为什么它只适用于可编程评估器。
- 使用标准库实现一个玩具 HTN 规划器和一个玩具进化搜索。

## 问题

ReWOO（课程 02）、规划与执行以及 ReAct 覆盖了大多数智能体规划。有两种情况它们无法很好地处理：

1. **具有可证明正确性的计划。** 调度、飞行路径规划、合规工作流——计划必须在构造上就是正确的。一个偶尔会幻想出步骤的流畅 LLM 计划是不可接受的。
2. **具有可机器检查适应度函数的优化。** 矩阵乘法、调度启发式、编译器遍历——目标不是“一个正确的计划”，而是“最佳计划”。

HTN 规划和 AlphaEvolve 解决了这两个不同的问题。两者都使用 LLM 作为放大器，而不是替代品。

## 概念

### 层次任务网络

一个 HTN 包括：

- **任务**——复合任务（待分解）和原始任务（可直接执行）。
- **方法**——将复合任务分解为子任务的方法，带有前置条件。
- **算子**——具有前置条件和效果的原始动作。
- **状态**——一组事实。

规划：给定一个目标任务和一个初始状态，找到一个分解为原始算子的序列，其前置条件按顺序得到满足。

HTN 比 LLM 更早出现，至今仍是可证明正确计划的参考标准。

### ChatHTN（Gopalakrishnan 等，2025）

ChatHTN（arXiv:2505.11814）将符号 HTN 与 LLM 查询交错进行：

1. 尝试使用现有方法分解当前复合任务。
2. 如果没有方法适用，则询问 LLM：“在状态 `s` 中你会如何分解 `task`？”
3. 将 LLM 响应转换为候选子任务。
4. 根据算子模式进行验证；拒绝无效分解。
5. 递归。

论文的核心主张：产生的每个计划都是可证明正确的，因为 LLM 建议仅作为候选分解进入，从不直接编辑计划。符号层负责正确性；LLM 扩展方法库。

在线方法学习（OpenReview `gwYEDY9j2x`，2025 后续）添加了一个学习器，通过回归泛化 LLM 产生的分解——将 LLM 查询频率降低高达 75%。

### AlphaEvolve（Novikov 等，2025）

AlphaEvolve（arXiv:2506.13131，DeepMind，2025 年 6 月）是一个不同的野兽：由 Gemini 2.0 Flash/Pro 集群编排的进化代码搜索。

循环：

1. 从一个种子程序 + 一个可编程评估器（返回适应度分数）开始。
2. LLM 集群提议突变。
3. 通过评估器运行突变。
4. 保留最佳；再次突变。

已发布的成果：

- 56 年来首次改进 4x4 复数矩阵乘法的 Strassen 算法（48 次标量乘法）。
- 通过 Borg 调度启发式恢复了 0.7% 的 Google 计算资源。
- 在前沿工作负载上实现了 32% 的 FlashAttention 加速。

硬约束：适应度函数必须是可机器检查的。对散文答案进行进化搜索不会收敛。

### 何时使用哪种方法

| 问题类别 | 使用方法 | 原因 |
|----------|----------|------|
| 具有硬约束的调度 | HTN + ChatHTN | 可证明的正确性 |
| 编译器优化 | AlphaEvolve | 可机器检查的适应度 |
| 多步骤任务执行 | ReAct / ReWOO | LLM 在循环中，无正式保证 |
| 带测试的代码改进 | AlphaEvolve | 测试即评估器 |
| 策略绑定的自动化 | HTN | 前置条件编码策略 |

### 该模式可能出错的地方

- **没有算子的 HTN。** 没有前置条件/效果模式，正确性主张就会崩溃。ChatHTN 的“LLM 建议分解”需要模式来拒绝无效移动。
- **没有真正评估器的 AlphaEvolve。** “询问 LLM 代码是否更好”不是适应度函数。评估器必须是确定性的且快速的。
- **过度工程化。** 大多数智能体任务两者都不需要。首先尝试 ReAct 或 ReWOO。

## 构建它

`code/main.py` 实现了两个玩具：

- 一个标准库 HTN 规划器，包含算子、方法、前置条件、效果，以及一个在没有方法匹配复合任务时启动的 `LLMFallback`。“LLM”是一个脚本化的分解器，因此规划器可以离线运行。
- 一个标准库进化搜索，针对算术程序：增长表达式，使其输出在测试集上最小化 `|f(x) - target|`。评估器是确定性的。

运行它：

```
python3 code/main.py
```

跟踪显示了 HTN 规划器分解复合任务（带有计划中期的 LLM 回退）以及进化循环收敛到目标表达式。

## 使用它

- **HTN 规划器** —— `pyhop`、`SHOP3`，或为特定领域的策略执行构建自己的。
- **ChatHTN** —— 研究代码；该模式（符号 + LLM 回退）可以干净地移植到任何 HTN 规划器。
- **AlphaEvolve** —— DeepMind 论文；该模式（集群 + 评估器）是可复制的。OpenEvolve 和类似的开源分支正在出现。
- **智能体框架** —— 目前没有提供一流的 HTN 或 AlphaEvolve。将其构建为子智能体或后台工作者。

## 交付它

`outputs/skill-hybrid-planner.md` 生成一个混合规划器脚手架（HTN 或进化式），其中 LLM 的角色被明确限定。

## 练习

1. 扩展 HTN 规划器以支持回溯：当算子的后置条件在运行时失败时，回滚并尝试下一个方法。
2. 为 ChatHTN 添加一个 LLM-方法缓存：当 LLM 在状态模式 `P` 中分解任务 `T` 时，存储结果。下次调用时首先重新检查方法库。
3. 将进化搜索评估器替换为真实的测试套件。进化一个通过 20 个测试用例的排序函数；报告收敛所需的代数。
4. 阅读 AlphaEvolve 的评估器设计说明。为你关心的领域（SQL 查询优化、测试套件最小化、部署 YAML）设计一个评估器。
5. 结合使用：使用 HTN 将复合任务分解为子任务，然后对每个子任务的原始算子使用进化搜索。它在哪些地方表现出色，在哪些地方过度工程化？

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|----------|
| HTN | “层次规划器” | 带有算子、前置条件、效果的任务分解 |
| 方法 | “分解规则” | 将复合任务分解为子任务的方法 |
| 算子 | “原始动作” | 带有前置条件和效果的具体步骤 |
| ChatHTN | “LLM + HTN” | 符号规划器在没有方法匹配时询问 LLM |
| AlphaEvolve | “进化代码搜索” | 集群 LLM 突变代码；确定性评估器选择 |
| 适应度函数 | “评估器” | 对输出的确定性、可机器检查的分数 |
| 在线方法学习 | “缓存的 LLM 分解” | 存储 + 泛化 LLM 计划以降低查询成本 |
