# LLM FinOps — 单位经济学与多租户归因

> 传统 FinOps 在 LLM 支出上失效。成本是 token 交易，不是资源运行时间。标签无法映射 — 一次 API 调用是一笔交易，不是一个资产。工程决策（提示设计、上下文窗口、输出长度）就是财务决策。2026 年的操作手册有三个归因维度，需在第一天就接入：按用户（`user_id`）用于席位定价和扩展，按任务（`task_id` + `route`）用于产品功能成本和优先级排序，按租户（`tenant_id`）用于单位经济学和续约。四个 token 层 — 提示、工具、记忆、响应 — 混在一个桶里会隐藏支出。多租户产品的执行阶梯：每租户速率限制（预期峰值的 2-3 倍，返回 429 + `Retry-After`）；每日支出上限（合同上限的 1.5-3 倍；触发速率收紧 + 告警）；支出 z-score > 4 时的终止开关（自动暂停 + 呼叫值班）。归因模式：标签聚合、遥测关联（trace-ID → 计费；最高精度）、采样推断、基于模型的分配、事件溯源、实时流。单位指标：每解决查询成本、每生成产物成本 — 而不是 $/M tokens。事后标记总是遗漏；在请求创建时接入。

**类型：** 学习
**语言：** Python（stdlib，带终止开关的玩具成本归因模拟器）
**前置课程：** 第 17 阶段 · 13（可观测性），第 17 阶段 · 14（缓存）
**时间：** ~60 分钟

## 学习目标

- 解释为什么传统 FinOps（标签 + 分层）在 LLM 支出上失效，并命名三个新的归因维度。
- 枚举四个 token 层（提示、工具、记忆、响应）以及为什么单桶计费隐藏成本。
- 为多租户产品设计执行阶梯（速率 → 支出上限 → 终止开关）。
- 选择单位指标（每解决查询/产物成本）而不是 $/M tokens。

## 问题

你的账单显示 $40,000。你不知道：
- 哪个租户花了这笔钱。
- 哪个产品功能驱动了这笔支出。
- 是否有任何单个用户在滥用。
- 是提示膨胀、工具调用还是记忆放大导致了问题。

在提供商侧进行标签聚合对云资源（EC2、S3）有效，因为标签会传播到明细项。LLM API 调用不会自动标记 — 你必须在调用点盖上用户/任务/租户标记并一路携带。事后归因总是遗漏边界情况。

## 概念

### 三个归因维度

**按用户**（`user_id`）：谁花了什么。驱动席位定价、扩展对话、识别高价值用户。

**按任务**（`task_id` + `route`）：哪个产品功能花了什么。驱动功能优先级、砍掉昂贵功能的决策。

**按租户**（`tenant_id`）：哪个客户是盈利的。驱动单位经济学、续约定价、分层阈值。

第一天就在调用点接入全部三个。事后总是更差。

### 四个 token 层

| 层 | 示例 | 典型占比 |
|----|------|---------|
| 提示 | system + 用户输入 | 40-60% |
| 工具 | 工具调用结果回传 | 20-40%（Agent 工作负载） |
| 记忆 | 先前对话 / 检索文档 | 10-30% |
| 响应 | 模型输出 | 10-30% |

将四层混在一起会让优化变成盲区。在归因方案中拆分它们。

### 执行阶梯

1. **速率限制** — 每租户。预期峰值的 2-3 倍。返回 429 并附带 `Retry-After`。租户感受到摩擦；没有意外账单。

2. **每日支出上限** — 每租户。合同上限的 1.5-3 倍。触发条件：收紧速率限制 + 告警客户成功团队。

3. **终止开关** — 支出 z-score 相对租户基线 > 4 时触发。自动暂停租户；呼叫值班；升级至运维 + 客户成功。

### 归因模式

- **标签聚合**：在元数据头盖章；事后聚合。简单；粗糙。
- **遥测关联**：通过 trace ID 将链路关联到计费。最高精度。成熟团队的做法。
- **采样 + 推断**：采样 5-10%，乘以系数。粗略支出的成本效益最优；会遗漏尾部。
- **基于模型的分配**：回归推断成本驱动因素。用于无标签的遗留数据。
- **事件溯源**：成本作为流中的事件（Kafka / Kinesis）。实时。
- **实时流**：仪表板亚秒级更新。

### 每 X 成本是单位指标

$/M tokens 是厂商术语。产品指标：

- 每解决工单成本。
- 每生成文章成本。
- 每成功 Agent 任务成本。
- 每用户会话分钟成本。

将成本与产品产出挂钩。否则优化没有锚点。

### 成本归因链路形态

```
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

每次调用都发出。存储在数据湖中。按维度聚合。第 17 阶段 · 13 的可观测性栈是其所在。

### 复合节省栈

栈：缓存 + 批处理 + 路由 + 网关。四项叠加：
- 缓存 L2（第 17 阶段 · 14）：输入成本约降低 10 倍。
- 批处理（第 17 阶段 · 15）：减免 50%。
- 路由到廉价模型（第 17 阶段 · 16）：成本降低 60%。
- 网关效率（第 17 阶段 · 19）：冗余 + 重试。

最佳情况叠加：可达到朴素基线的约 5-10%。大多数团队有 2-3 个杠杆在用；很少有团队四项全部叠加。

### 需要记住的数字

- 归因维度：按用户、按任务、按租户。
- 四个 token 层：提示、工具、记忆、响应。
- 终止开关：支出 z-score > 4。
- 单位指标：每解决查询成本，不是 $/M tokens。
- 叠加优化：可达基线的约 5-10%。

## 关键术语

| 术语 | 通俗说法 | 实际含义 |
|------|---------|---------|
| 按用户归因 | "用户级成本" | 每次调用盖上 `user_id` |
| 按任务归因 | "功能成本" | `task_id` + `route` 标识产品功能 |
| 按租户归因 | "客户成本" | `tenant_id`；驱动单位经济学 |
| 四个 token 层 | "成本层" | 提示 + 工具 + 记忆 + 响应 |
| 速率限制 | "429 保护" | 在网关执行的每租户上限 |
| 每日支出上限 | "每日上限" | 租户范围的预算带告警 |
| 终止开关 | "自动暂停" | 支出 z-score > 4 触发自动暂停 |
| 每解决成本 | "产品单位指标" | 与产品产出挂钩的成本，非 token |
| 遥测关联 | "链路转计费" | 最高精度归因模式 |
| 叠加优化 | "缓存+批处理+路由+网关" | 复合节省至基线的约 5-10% |
