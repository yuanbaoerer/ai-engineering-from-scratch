# vLLM 推理内部机制学习笔记

> 日期: 2026-06-12

## 1. PagedAttention：KV Cache 的内存管理

**核心问题**：传统方法为每个请求预分配最大序列长度的连续内存，导致 80% 内存浪费。

**解决方案**：借鉴操作系统虚拟内存机制，将 KV cache 拆分成固定大小的块（16 token 一块），按需分配。

**关键概念**：

| 概念 | 类比 | 作用 |
|------|------|------|
| 块（Block） | 格子 | 固定 16 token 的内存单元 |
| 块表（Block Table） | 借阅记录 | 逻辑 token 位置 → 物理块的映射 |
| 空闲池 | 仓库 | 已完成序列释放的块，供新请求使用 |

**效果**：碎片率从 60-80% 降至 <4%，内存利用率从 20% 提升至 96%。

## 2. PagedAttention 的生活类比

**酒店 vs 共享单车**：
- 传统方法 = 租整套公寓，空着也付费
- PagedAttention = 共享单车，扫码骑走，用完还车，按需计费

**本质**：从"预留整块资源"变成"按需分配小单元"。

## 3. Continuous Batching：动态批处理

**核心问题**：静态批处理要求所有人完成才能处理下一批，快速用户干等。

**解决方案**：每次解码迭代后重新调度，完成的序列立即离开，新请求立即加入。

**关键机制**：
1. **释放**：请求完成或达到 max_tokens → 立即离开
2. **接纳**：有空闲 KV 块 → 新请求立刻进来
3. **每轮调度**：每次解码后重新决策，不等所有人

**公交模型**：乘客随上随下，车不停。

## 4. Continuous Batching 的本质

**核心洞察**：单个用户的算力需求不足以占满 GPU，所以把剩余算力分配给其他用户。

```
单个用户：只用了 15% 算力
多人并发：多个用户共享，GPU 利用率 90%+
```

**并发限制的必要性**：GPU 内存有限，必须限制最大并发数（如 40-50 个），否则所有请求都变慢。

## 5. Chunked Prefill：长任务切片

**核心问题**：长提示的 prefill 会卡住其他用户的 decode，导致延迟抖动。

**解决方案**：将长 prefill 切成 512-token 切片，每片之间穿插 decode 操作。

**效果**：
- 无 chunked prefill：P99 ITL ≈ 50ms
- 有 chunked prefill：P99 ITL ≈ 15ms

**不影响完整性**：切片只是分批计算，每个 token 的 KV 最终都会算完，结果完全相同。

## 6. 三者如何协同

| 特性 | 解决的问题 | 效果 |
|------|-----------|------|
| PagedAttention | 内存碎片浪费 | 同显存多服务 3-4× 用户 |
| Continuous Batching | GPU 空转等待 | GPU 利用率 50% → 90%+ |
| Chunked Prefill | 长任务卡住别人 | 延迟 50ms → 15ms |

**一句话总结**：用同样的 GPU 钱，服务更多人，每人体验更好。

## 7. 生产环境的关键参数

| 参数 | 作用 | 典型值 |
|------|------|--------|
| `--gpu-memory-utilization` | KV cache 占 HBM 比例 | 0.9 |
| `--max-num-seqs` | 最大并发序列数 | 40 |
| `--max-num-batched-tokens` | 每批最大 token 数 | 8192 |

**v0.18.0 限制**：`--enable-chunked-prefill` 与 draft model 投机解码不能同时启用。

## 8. 性能基准数据

| 场景 | 吞吐量 |
|------|--------|
| 三者全开 (H100 + Llama 3.3 70B FP8) | 2,200-2,400 tok/s |
| 默认 vLLM（无 chunked prefill） | ~1,800 tok/s |
| 朴素 PyTorch 循环 | ~600 tok/s |

## 9. 前沿方向

vLLM 还未榨干硬件能力，主要前沿方向：

- **投机解码**：小模型猜，大模型验，延迟降低 2-3×（已实用）
- **稀疏注意力**：不算全部 token，计算量减半
- **混合专家（MoE）**：只激活部分参数，吞吐提升 3-5×
- **新架构（Mamba/RWKV）**：O(n) 复杂度，可能颠覆 Transformer
