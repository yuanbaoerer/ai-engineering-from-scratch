# 面向 AI 的 SRE —— 多智能体事件响应、运维手册与预测性检测

> AI SRE 利用通过 RAG（检索增强生成）技术与基础设施数据（日志、运维手册、服务拓扑）相结合的 LLM，实现事件调查、文档记录和协调阶段的自动化。2026 年的架构模式是多智能体编排（Multi-Agent Orchestration）——由一个监督者（Supervisor）协调专门的智能体（日志智能体、指标智能体、运维手册智能体）；AI 提出假设和查询，人类批准判断性决策。Datadog Bits AI 和 Azure SRE Agent 已作为托管产品推出了此功能。运维手册（Runbooks）正在不断演进：NeuBird Hawkeye 使用对抗性评估（Adversarial Evaluation）（两个模型分析同一事件；意见一致代表高置信度，意见不一致则上报）；操作记忆（Operational Memory）在团队人员变动时得以保留。自动修复（Auto-Remediation）仍然保持谨慎：AI 建议，人类批准。完全自主的行动仅限于狭窄范围（重启 Pod、回滚特定部署）并受严格约束——任何宣称“一劳永逸”的方案都属于过度宣传。新兴前沿：事件前预测（Pre-incident Prediction）。麻省理工学院（MIT）的研究报告称，一个基于历史日志、GPU 温度和 API 错误模式训练的 LLM，在测试集中提前 10-15 分钟预测了 89% 的故障。预测：到 2026 年底，95% 的企业级 LLM 将具备自动故障转移能力。

## 学习目标

- 绘制多智能体 AI SRE 架构图：监督者 + 专门智能体（日志、指标、运维手册）+ 人类批准门禁。
- 解释为什么自动修复是狭窄范围的（重启 Pod、回滚部署）而非大范围的（重新架构服务）。
- 阐述对抗性评估模式（NeuBird Hawkeye）：两个模型意见一致 = 高置信度；意见不一致 = 上报。
- 引用麻省理工学院（MIT）89% 早期检测率的研究结果及其操作约束：没有执行动作的预测仅仅是仪表盘。

## 问题所在

一位值班工程师在凌晨 3 点收到页面警报。“结账流程错误率过高。”他检查了 Datadog、Loki、三本运维手册和部署日志。30 分钟后，他发现根本原因是由于 KV 缓存激增导致的 vLLM OOM。他重启了 Pod；错误清除了。

在 2026 年，这个调查过程的前 20 分钟是可自动化的。按服务对日志进行分组、与最近的部署进行关联、与运维手册进行匹配——这些都是 RAG + 工具调用的应用场景。一个监督智能体可以在人类打开 Datadog 之前完成初步分级并提出假设。

完全自主的修复则是一个不同的问题。重启 Pod：安全。在策略允许的范围内扩展 GPU 池：安全。重新架构服务：绝对不行。关键在于划清这条狭窄的界限。

## 核心概念

### 多智能体架构

```
          事件
             │
             ▼
        监督者 (Supervisor)
        /    |    \
       ▼     ▼     ▼
  日志智能体  指标智能体  运维手册智能体
       │     │     │
       └─────┴─────┘
             │
             ▼
        假设 + 证据
             │
             ▼
        人类批准
             │
             ▼
        行动（狭窄范围）
```

监督者将事件分解为子查询。专门的智能体拥有工具访问权限（日志搜索、PromQL、文档检索）。监督者进行综合分析，并将假设 + 证据呈报给人类。人类批准或重定向。

### 自动修复范围

**安全（狭窄范围）**：重启 Pod、回滚特定部署、在预批准范围内扩展资源池、启用预批准的功能开关。

**不安全（大范围）**：更改服务拓扑、修改资源限制、部署新代码、更改 IAM 权限、修改数据库。

任何宣称“一劳永逸”的方案都属于过度宣传。随着 AI SRE 的成熟，安全操作集合会扩大，但这条边界是真实存在的。

### 对抗性评估（NeuBird Hawkeye）

两个模型独立分析同一事件。如果它们对根本原因的判断一致，则置信度较高。如果判断不一致，则在显示两个假设的同时上报给人类。这是一个简单但有效的模式，用于过滤幻觉导致的错误根因。

### 操作记忆（Operational Memory）

团队人员流动是传统 SRE 的隐形杀手——部落知识会随之流失。AI SRE 将运维手册和事后复盘（Post-mortems）存储在向量数据库中；智能体在每次新事件发生时都会检索这些信息。当新工程师加入时，AI 拥有完整的历史记录。

### 事件前预测（Pre-incident Prediction）

麻省理工学院 2025 年的研究：一个基于历史日志、GPU 温度和 API 错误模式训练的 LLM，在测试集中提前 10-15 分钟预测了 89% 的故障。

现实情况：没有执行动作的预测只是仪表盘。操作性问题是“当我们预测时，我们该做什么？”预先排空节点？发送寻呼？自动扩缩容？答案取决于具体的策略。

### 2026 年的产品

- **Datadog Bits AI** —— Datadog 内置的托管 AI SRE 副驾驶。
- **Azure SRE Agent** —— Azure 原生。
- **NeuBird Hawkeye** —— 对抗性评估 + 操作记忆。
- **PagerDuty AIOps** —— 分级 + 去重。
- **Incident.io Autopilot** —— 事件指挥官 + 协调。

### 运维手册即代码（Runbooks as Code）

运维手册从 Confluence 页面演变为带有结构化部分（症状、假设、验证、行动）的版本化 Markdown。结构化的运维手册能提供更好的 RAG 检索效果。开始部署任何 AI SRE 系统的第一步，就是将非结构化运维手册转化为结构化版本。

### 您应该记住的数字

- MIT 早期检测：89% 的故障，提前 10-15 分钟预警。
- 多智能体分级：监督者 + （日志、指标、运维手册）+ 人类。
- 安全的自动修复集合：重启 Pod、回滚部署、在范围内扩展。
- 对抗性评估：两个模型独立分析；一致 = 高置信度。

## 使用它

`code/main.py` 模拟了一个多智能体分级过程：日志智能体发现错误，指标智能体发现 CPU 激增，运维手册智能体匹配到已知问题。监督者对假设进行排序。

## 交付它

本课程产出 `outputs/skill-ai-sre-plan.md`。根据当前的值班安排、事件量和团队成熟度，设计一个 AI SRE 部署方案。

## 练习

1. 运行 `code/main.py`。如果日志智能体和指标智能体的结论不一致怎么办？监督者如何解决？
2. 为您的服务定义三个“安全”的自动修复行动。并说明理由。
3. 编写一个结构化的运维手册模板：包含哪些部分、必填字段以及验证命令。
4. 预测性检测触发，提前时间为 12 分钟。您的策略是什么——寻呼、预先排空，还是两者兼有？
5. 论证一个 3 人的团队应该在 2026 年采用 AI SRE 还是等待。请考虑成熟度、事件量和风险。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| AI SRE | “用于值班的智能体” | 基于 LLM 的事件调查 + 协调 |
| 监督智能体 (Supervisor agent) | “编排器” | 将事件分解为子查询的顶层智能体 |
