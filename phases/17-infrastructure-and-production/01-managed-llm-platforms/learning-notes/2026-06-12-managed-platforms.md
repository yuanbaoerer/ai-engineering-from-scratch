# 托管 LLM 平台选型学习笔记

> 日期: 2026-06-12

## 1. 三大平台策略

| 平台 | 策略 | 特点 |
|------|------|------|
| **AWS Bedrock** | 模型市场 | 多模型（Claude/Llama/Titan/Mistral）一个 API 调用，Application Inference Profiles 提供清晰成本归属 |
| **Azure OpenAI** | 独家合作 | 只有 OpenAI 模型（GPT-4/5），PTU 提供专用容量，延迟最低（~50ms 中位数） |
| **Vertex AI** | Gemini 优先 | 多模态长上下文（1M token），Model Garden 支持第三方模型，BigQuery 灵活归属 |

## 2. PTU 是预留容量，不是响应时间

**PTU = Provisioned Throughput Unit**：付费预留的一块 GPU 推理资源。

| | 按需（On-Demand） | PTU |
|---|---|---|
| 容量 | 共享，与他人竞争 | 专用，你独占 |
| 计费 | 按 token/请求 | 按小时预留（空闲也付费） |
| 延迟 | 波动大（受流量影响） | 稳定（如 Azure ~50ms） |

**类比**：PTU 是"买断一台服务器"vs"排队用共享电脑"的区别。GPU 始终为你保留，请求到达即可处理，首 token 延迟更低更稳定。

## 3. 延迟指标：TTFT 和 P99

| 缩写 | 全称 | 含义 |
|------|------|------|
| **TTFT** | Time To First Token | 首 token 延迟 - 从发送请求到收到第一个 token 的时间 |
| **P99** | 99th Percentile | 第 99 百分位 - 99% 的请求都在此延迟内完成 |
| **SLA** | Service Level Agreement | 服务级别协议 - 你对用户承诺的延迟上限 |

**示例**：SLA 承诺 P99 < 100ms = "99% 的用户等待不超过 100ms"

## 4. 盈亏平衡：PTU 何时划算

PTU 是固定成本（$10/小时 = $240/天），按需是可变成本。

**盈亏平衡点**：约 40-60% 利用率

- **<50% 利用率**：按需更便宜（避免为空闲容量付费）
- **>60% 利用率**：PTU 更便宜（节省高达 70%）
- **可预测的高流量**：用 PTU
- **突发或低流量**：用按需

## 5. Prompt Caching 命中机制

**核心**：让每个请求的前缀（prefix）尽量相同。

### 高命中策略

1. **固定 System Prompt**：每次都用完全相同的指令和格式
2. **保持请求结构一致**：模板固定，只换变量
3. **5 分钟窗口**：Cache 有写入成本，需在窗口内重复使用才划算
4. **原子化动态内容**：待处理内容放末尾，保持短且独立

### 最佳实践结构

```
固定前缀（长）+ 动态内容（短、原子）
   ↓
高 cache 命中
```

**盈亏平衡**：同一前缀用 2 次以上就划算。

## 6. 前缀与动态内容占比

| 占比 | 适用场景 |
|------|---------|
| **前缀 70-80%** | 大批量处理（50k+ 文档），cache 收益最大 |
| **前缀 50-60%** | 中等批量，平衡 cache 和 token 利用率 |
| **前缀 <40%** | 小批量或动态内容本身很长，cache 不划算 |

**原则**：先保证指令清晰、格式明确、few-shot 示例完整，再优化比例。

## 7. 双提供商最低要求策略

**为什么**：
- 单一平台 = 厂商锁定 = 被排除 2/3 前沿模型
- 云服务故障时有发生（Azure OpenAI 2025 年 1 月事件、AWS us-east-1 故障）
- 模型季度轮换：Claude 3.7 → Gemini 2.5 → GPT-5

**成本**：
- 网关开销：~3%
- 空闲备用余量：~10%
- **总增加：~13%**

**业务案例**：13% 成本增加是保险，防止客户流失、SLA 赔偿、应急响应时间。
