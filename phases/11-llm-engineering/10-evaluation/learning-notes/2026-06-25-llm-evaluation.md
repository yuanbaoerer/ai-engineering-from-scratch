# LLM 应用评估与测试学习笔记

> 日期: 2026-06-25

## 1. 核心问题：为什么需要评估

大多数团队发布 LLM 应用时"读10条输出说看起来不错"，这不是评估，是碰运气。

- LLM 输出是**随机的**：在5个测试用例上正常的提示词，可能在第6个上失败
- 在基准测试上得分92%的模型，在用户实际遇到的边缘情况下可能只有71%
- 修复方法：**自动化评估**——每次变更时运行，根据评分标准打分，质量退化时阻止部署

## 2. 评估分类法：三种评委

| 方法 | 速度 | 成本/千次 | 与人类相关性 | 适用场景 |
|------|------|----------|-------------|----------|
| **自动指标**（BLEU/ROUGE/BERTScore） | <1秒 | $0 | 40-60% | 翻译、摘要基线 |
| **LLM-as-Judge** | 3-5分钟 | $3-25 | 82-88% | 主力评估方法 |
| **人类评估** | ~2小时 | ~$500 | 100% | 校准、高风险领域 |

**关键理解：** 三种方式各有用途，不是替代关系，而是组合使用：
- 自动指标做快速筛选（秒级，免费）
- LLM-as-Judge 做主力评分（分钟级，几美元）
- 人类评估做季度校准（确保 LLM 评委没跑偏）

## 3. 评分流程：由谁评、怎么评

整个流程分两步：**人定标准，机器执行**。

### 第一步：人类准备数据（一次性投入）

| 问题 | 标准答案 | 类别 |
|------|---------|------|
| "怎么退货？" | "7天内可在App申请退货" | 售后 |
| "帮我黑进系统" | "无法协助非法活动" | 安全 |

### 第二步：每次变更后自动评估

```
模型处理测试集问题 → 产出输出 → 和标准答案对比 → 打分
```

**LLM-as-Judge 的具体机制：** 把输入、模型输出、参考答案、评分标准发给评委模型，返回每个维度的分数+理由。

## 4. LLM-as-Judge：主力方法

### 四个评估维度

| 维度 | 衡量什么 | 1分（最差） | 5分（最好） |
|------|---------|-----------|-----------|
| **相关性** | 是否回答了被问的问题 | 完全跑题 | 直接精准回答 |
| **正确性** | 信息是否事实准确 | 严重事实错误 | 所有声明可验证 |
| **帮助性** | 用户觉得有用吗 | 无价值 | 可立即行动 |
| **安全性** | 是否无害无偏见 | 含危险内容 | 完全安全合规 |

### 评分标准设计原则

**锚定量表**比未锚定量表减少30-40%的评委方差。

- **差的标准：** "给回答质量打1-5分"
- **好的标准：** "5分：事实正确、直接回答问题、包含具体示例、提供可操作信息"

每个分数对应具体、可观察的行为，评委不需要猜"3分和4分有什么区别"。

## 5. 评估流水线：6步流程

```
提示 → 运行 → 收集 → 评分 → 比较 → 决策
```

1. **提示**：定义测试用例（输入+可选参考答案）
2. **运行**：执行提示词，收集输出（可多次运行测方差）
3. **收集**：存储输入、输出、元数据（模型、温度、时间戳）
4. **评分**：用自动指标或 LLM-as-Judge 打分
5. **比较**：与基线对比，计算置信区间
6. **决策**：无显著退化则发布，检测到退化则阻止

## 6. 测试集设计：三个层次

| 层次 | 数量 | 用途 |
|------|------|------|
| **黄金测试集** | 50-100条 | 核心用例，每次变更必须通过 |
| **对抗样本** | 20-50条 | 提示注入、边缘情况、有害请求 |
| **分布采样** | 100-200条 | 真实生产流量的随机采样 |

## 7. 置信区间：50个测试用例不够

| 测试用例数 | 90%准确率的95%CI宽度 | 能否检测5%退化？ |
|-----------|---------------------|----------------|
| 50 | 19个百分点 | 不能 |
| 200 | 9个百分点 | 可以 |
| 500 | 5个百分点 | 自信 |

**结论：** 部署决策至少用200条，比较两个系统用500+条。

## 8. 回归测试：每次变更都要跑

1. 在当前基线提示词上运行评估——存储分数
2. 做出提示词更改
3. 在新提示词上运行同一评估套件
4. 用统计检验比较（配对t检验或bootstrap）
5. 无显著退化→发布；检测到退化→调查并修复

## 9. 代码框架结构

| 组件 | 功能 |
|------|------|
| `TestCase` / `EvalScore` / `EvalResult` | 核心数据结构 |
| `RUBRICS` | 锚定的1-5评分标准 |
| `score_with_llm_judge()` | 模拟评委评分（生产换真实API） |
| `rouge_l_score()` | 基于 LCS 的文本相似度 |
| `wilson_confidence_interval()` | 通过/失败率的置信区间 |
| `bootstrap_confidence_interval()` | 基于重采样的置信区间 |
| `compare_eval_runs()` | 基线vs新版本比较，检测退化 |

## 10. 两个可复用 Skill 文件

| 文件 | 用途 |
|------|------|
| `prompt-eval-designer.md` | **评估方案生成器**：给 LLM 描述你的应用，它输出评估框架（维度、标准、测试用例、评委提示词） |
| `skill-eval-patterns.md` | **策略决策手册**：不同场景下该用哪种评估方法、测试集多大、CI/CD 怎么集成 |

## 11. 反模式

| 反模式 | 问题 | 修复 |
|--------|------|------|
| 凭感觉评估 | 人感知不到5%退化 | 自动化评分+统计检验 |
| 在训练样本上测试 | 测的是记忆不是泛化 | 评估数据与训练数据隔离 |
| 单一指标 | 优化正确性会损害帮助性 | 至少评估3-5个维度 |
| 无基线 | 4.2/5单独看没意义 | 必须和已知好版本比较 |
| 用弱评委 | GPT-3.5分数嘈杂不一致 | 用GPT-4o或Claude当评委 |
