# 上下文工程学习笔记

> 日期: 2026-06-16

## 1. 上下文工程 vs Prompt 工程

Prompt 工程只是子集。上下文工程是整盘游戏——决定什么进入上下文窗口、以什么顺序、以什么优先级进入。上下文 = 系统指令 + 检索文档 + 工具定义 + 对话历史 + 少样本示例 + prompt 本身。

拥有 200K token 窗口不意味着使用 200K 是有效的。精心策划的 10K 通常优于随意填充的 100K。

## 2. 中间丢失效应（Lost-in-the-Middle）

Liu et al. (2023) 的研究发现：LLM 对上下文**开头和结尾**关注更好，中间 40-70% 位置的信息检索准确性下降 10-20%。

工程含义：
- 最重要的信息放**前面**（系统 prompt、关键指令）
- 当前查询和最相关上下文放**最后**（近因偏差有帮助）
- 中间视为**最低优先级区域**
- 如果必须在中间放信息，在结尾重复关键点

## 3. 重排序判断重要性的方法

文档中的 `score_relevance` 使用**词重叠**（查询词与文档词的交集比例），这是教学简化。生产系统中的判断方法：

| 方法 | 说明 |
|------|------|
| **向量嵌入余弦相似度** | 查询和文档编码为向量，计算余弦距离 |
| **BM25** | 经典信息检索算法，考虑词频和文档频率 |
| **Cross-Encoder 重排** | 专门的重排模型对查询-文档对联合编码打分 |
| **LLM 自评** | 让模型直接判断相关性 |

## 4. BM25 算法

基于词频（TF）和逆文档频率（IDF），但比 TF-IDF 更精细：

```
score(Q, D) = Σ IDF(q) · [ f(q,D) · (k₁+1) ] / [ f(q,D) + k₁·(1-b+b·|D|/avgdl) ]
```

相比 TF-IDF 的改进：
- **词频饱和**：`k₁` 参数控制词频增长到一定程度后收益递减（第 10 次出现的意义远小于第 1 次）
- **文档长度归一化**：`b` 参数惩罚过长文档，避免偏向长文档

局限：BM25 是词法匹配，"car" 和 "automobile" 得分为 0，不理解语义。

## 5. LLM 意图理解的来源

意图理解不是单独训练出来的，是**预训练的涌现能力**。

- 训练目标：下一个 token 预测
- 为了准确预测下一个 token，模型必须理解当前文本在做什么（任务类型、用户意图）
- 意图理解内化在参数中，没有显式的"意图分类器"
- 指令微调（SFT）进一步强化了按意图产生对应输出格式的能力

## 6. 单向注意力与意图理解

主流 LLM（GPT、Claude、Llama）都是**单向注意力**（Causal Attention），只能看到左边的 token。

单向 ≠ 理解能力差。当模型处理到句子末尾时，所有前面的词都在上下文中了，完全能理解完整意图。BERT 的双向注意力对生成任务无用，因为生成必须逐 token 进行。

意图理解能力的差异主要来自**模型规模**（层数、参数量），而非注意力方向。

## 7. 动态上下文组装

核心思想：不同查询需要不同的上下文，不要每次都用静态填充。

执行流程：
1. 分类查询意图
2. 选择相关工具（不加载全部）
3. 检索相关文档（不加载固定集合）
4. 筛选相关历史轮次
5. 添加匹配的少样本示例
6. 按重要性重排序位置

效果：同一个模型，静态 20K token 信噪比低，动态 8K token 信噪比高。

## 8. 重排序的两层含义

重排序解决两个不同的问题：

| | 相关性重排（Selection） | 位置重排（Positioning） |
|--|----------------------|----------------------|
| **解决什么** | 选哪些文档 | 放在窗口哪里 |
| **核心价值** | 去噪、提高信噪比 | 缓解中间丢失 |
| **方法** | Cross-Encoder / LLM 打分 | 首尾高分、中间低分 |
| **重要性** | 主要作用 | 辅助作用 |

**选对文档远比放对位置重要。** 3 个相关文档即使全放中间，也比 10 个无关文档放在首尾效果好。

## 9. Claude Code 的上下文策略

Claude Code 没有显式的 cross-encoder 重排序，采用**基于工具的简单检索**：

- Grep/Glob 关键词搜索 → 读取匹配文件 → LLM 自己在推理时判断相关性
- 不预建向量索引，实时搜索文件系统
- 通过 CLAUDE.md 实现跨会话长期记忆
- 对话变长后旧轮次被摘要压缩

与 Cursor 的对比：Cursor 用向量嵌入 + 语义检索 + 重排序；Claude Code 把重排序的负担交给了 LLM 自身的注意力机制。

## 10. 技术选择要匹配数据特征

| 文档类型 | 信号特征 | 最佳检索方式 | 重排序必要性 |
|---------|---------|-------------|------------|
| 代码 | 结构化、有明确标识 | Grep/Glob | 不太需要 |
| 自然语言 | 语义模糊、同义词多 | 向量检索 + Cross-Encoder | 非常需要 |
| 表格/结构化数据 | 字段、数值、关系 | SQL/精确查询 | 不需要 |

代码的结构化信号（函数名、类名、文件路径）让简单搜索就够用；自然语言的语义模糊性让重排序成为必需。没有万能方案，只有适合场景的方案。
