# 高级 RAG 学习笔记

> 日期: 2026-06-17

## 1. 高级 RAG 的核心问题与四类技术

基础 RAG 只检索 top-k 最相似的块，在三种场景崩溃：**模糊查询**（"收入"vs"盈利"，用词不同）、**多跳问题**（答案分散在多块）、**大规模语料**（ANN 误差把正确块推出 top-k）。

根本原因：**向量相似 ≠ 相关性**。高级 RAG 用四类技术解决：

| 技术 | 解决的病 |
|------|---------|
| 混合搜索 | 检索方式不够（单靠向量漏精确匹配） |
| 重排序 | 初检精度低（双编码器漏 token 级交互） |
| 查询转换 | 查询本身太差（模糊查询落点偏离） |
| 父-子分块 | 检索粒度与生成粒度冲突 |

## 2. 向量搜索与 BM25 的合作

两者擅长相反、盲区互补：

| | 向量搜索（语义） | BM25（关键词） |
|---|---|---|
| 强项 | "取消订阅"匹配"终止计划" | "E-4021"精确匹配 |
| 盲区 | 把代码当噪声漏掉 | 零共同词则零结果 |

合作模式是**并行检索 → 各自排名 → RRF 融合**，不是串联。两路各取 `top_k * 3` 候选，故意多捞给融合留余量。

## 3. RRF 倒数排名融合

```
RRF_score(d) = Σ 1 / (k + rank_R(d))   （k 通常 60）
```

**用排名而非原始分数**——向量余弦分数（0~1）和 BM25 分数（几十上百）分布不同，直接加权无意义；换"第几名"拉到同一尺度。

| 文档 | 向量排名 | BM25 排名 | RRF 分数 |
|------|---------|----------|---------|
| A | 1 | 5 | 0.0318 |
| B | 3 | 2 | 0.0320 |

B 在两路都靠前（3、2），反超 A（1、5）——**惩罚"偏科"，奖励"两边共识"**。`k=60` 防止第 1 名过度主导。

## 4. HyDE 假设性文档嵌入

**别拿问题搜文档，先让 LLM 编一个"假答案"，拿假答案去搜真文档。**

核心洞察：**问题空间 ≠ 答案空间**。问题是疑问句、短、含"是什么"；答案是陈述句、长、满术语。两者在嵌入空间隔得远。假答案虽内容可能错，但语言结构、用词风格与真答案同类，落在"答案空间"附近，更易命中真块。

- 借的是 LLM 的**语言能力**（生成像答案的文本），不是**事实正确性**
- 假答案只用于检索阶段，最终喂 LLM 的仍是检索到的真实块，**幻觉不污染结果**
- 代价：多一次 LLM 调用，延迟 +500-2000ms
- 适用：模糊查询；不适用：精确术语查询（该用 BM25）

## 5. HyDE 为何不怕"语义相反"

关键区分嵌入模型编码的是**话题/语言结构语义**，不是**立场/真伪语义**：

- 假答案"企业**不能**退款" vs 真块"企业**能**退款" → 嵌入相似度**仍很高**，因为话题词（企业、退款、交易）重叠、语言结构同构，否定词权重小
- 嵌入衡量"是否谈同一件事"，不衡量"立场是否一致"

**真正害死 HyDE 的是主题漂移，不是立场相反**：
- LLM 把主题猜错（"苹果"猜成水果）→ 检索引到错误话题空间
- 精确术语查询（"E-4021"）→ 假答案里没有该字符串
- 多跳/比较问题 → 单个假答案无法代表"比较取最大"的结构

工程兜底：HyDE 只生成检索向量、不替换最终检索；多查询融合；仅模糊查询触发。

## 6. 父-子分块

**小块检索（精确命中），大块喂 LLM（充足上下文）。** 同一文档切两套粒度。

| 阶段 | 需求 | 选块 |
|------|------|------|
| 检索 | 小块聚焦，top-k 高相关 | 子块（如 50 词） |
| 生成 | 大块完整，LLM 有上下文 | 父块（如 200 词） |

数据结构：子块是父块的不重叠划分 + `child_to_parent` 映射表。向量索引**只放子块**，命中后查表返回父块。

代价：**存储翻倍**（子块向量索引 + 子块文本 + 父块文本 + 映射表）。

为何不直接大块检索：大块充满噪声，相似度被稀释，正确块易被挤出 top-k；小块信噪比高。

## 7. 父-子分块 vs 嵌套分块

**父子是嵌套的特例，但嵌套 ≠ 父子。**

- 结构上：父子就是两层嵌套（父含子、子是父的划分）
- 目的上：嵌套只是"块间有包含关系"的**结构描述**；父子是结构 + **检索协议**（检索子、返回父）

判断标准：若某实现只切了多层但检索直接返回命中层、无"命中细粒度→返回粗粒度"的跳转，它是嵌套分块但不是父子分块。

## 8. 交叉编码器 Cross-encoder

把查询和文档拼成一句话一起过 Transformer，靠 token 间全注意力捕捉细粒度交互，输出一个相关性分数（标量）。

```
[CLS] 查询 [SEP] 文档 [SEP] → Transformer → 相关性分数
```

对比双编码器：双编码器查询文档**各自独立编码**后算余弦，两者编码时互不可见，无法捕捉 token 级交互。交叉编码器让"盈利"token 直接 attend 到"4720"token，能判断"查询在问盈利，文档给了数字"。

本质是**二分类/打分任务**（在 MS MARCO 等数据上训练），专职相关性判别器，非通用编码器。

ColBERT 处于两者之间（后期交互多向量），是交互粒度的中间档。

## 9. Bi-encoder 粗筛 vs Cross-encoder 精筛

| 维度 | Bi-encoder（粗筛） | Cross-encoder（精筛） |
|---|---|---|
| 可预计算文档向量 | ✅ 能 | ❌ 不能 |
| 扫全库延迟 | 极快 | 慢 100-1000 倍 |
| token 级交互精度 | 低 | 高 |

```
全库 200万 → [Bi-encoder粗筛] → top-50 → [Cross-encoder精筛] → top-5 → LLM
```

- Bi-encoder **保召回**（宁滥勿缺，先把可能相关的捞进来）
- Cross-encoder **保精度**（宁缺勿滥，从噪声里挑出真答所问的）

**让它准的东西也正是让它慢的东西**（全交互结构既带来精度又导致无法预计算），所以必须搭配、不可互换。

## 10. 两个 encoder 在 RAG 系统的环节位置

RAG 分两条时间线：

```
【索引阶段·离线】文档 → 分块 → Bi-encoder嵌入 → 存向量库
【查询阶段·在线】查询 → 检索 → 生成 → 答案
```

- **Bi-encoder 横跨两阶段**：索引期算文档向量（离线、一次性），查询期算查询向量+比相似度（在线、快）。它是检索主力。
- **Cross-encoder 仅在查询阶段检索环节后半段**：作为 Bi-encoder 之后的二道筛子，不碰索引、不碰生成。

完整查询流：
```
查询 → [查询转换·HyDE/重写] → [检索]
        ① Bi-encoder粗筛 + BM25 → RRF → top-50
        ② Cross-encoder精筛 → top-5
        ③ 上下文组装（父-子分块在此返回父块）
     → [生成·LLM] → 答案
```

**两个 encoder 全在检索侧，生成是 LLM 独占。** 环节位置是能力结构的必然结果：可预计算 → Bi-encoder 必横跨两阶段；全交互 → Cross-encoder 必只能在线、只对小候选集。

## 11. 与 Phase 5-23 的关系

Phase 5-23 专攻"分块"这一件事（6 种算法 + 基准测试），Phase 11-07 把分块当组件，专攻"检索增强"的其他三件事（混合搜索、重排序、查询转换）。

**5-23 是分块的深度课，11-07 是检索的广度课，父-子分块是两者唯一接口。**

- 5-23 在最上游（索引阶段的分块环节），决定输入质量——块切错，后面重排序也救不回
- 11-07 的两个 encoder 在下游检索环节，决定"从这些块里挑出对的那个"
- 5-23 解决**块本身的信噪比**，11-07 解决**从块里捞出对的**
