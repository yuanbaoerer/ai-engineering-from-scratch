# 工具接口与并行调用学习笔记

> 日期: 2026-06-14

## 1. 工具接口四步循环

所有 function calling 机制（OpenAI、Anthropic、Gemini、MCP、A2A）底层都是同一个四步循环：

| 步骤 | 谁负责 | 做什么 |
|------|--------|--------|
| **Describe（描述）** | 宿主 | 用名称 + JSON Schema + 描述声明可用工具 |
| **Decide（决策）** | 模型 | 决定：直接回答、调用工具、还是拒绝 |
| **Execute（执行）** | 宿主 | 验证参数、运行真正的代码执行器 |
| **Observe（观察）** | 模型 | 拿到工具结果，生成回答或继续调用 |

这是整个第 13 阶段的不变量。

## 2. 四步循环 vs ReAct

两者不是包含关系，出发点不同：

- **ReAct** — 认知框架，强调 Thought（推理）→ Action → Observation 的 interleaving，关注"模型该怎么想"
- **四步循环** — 运行时协议，关注宿主和模型之间谁负责什么，Describe 和 Execute 是 ReAct 不关心的

实际生产中，ReAct 的 Thought 步骤往往被省略（纯 function calling 不要求模型输出 Thought）。

## 3. 宿主与模型的分工

- **模型（大脑）** — 理解意图、决定调哪个工具、生成回答
- **宿主（身体）** — 定义工具列表、执行调用、把结果喂回模型

模型不会"决定并行"——它只是在一次输出里写了多个调用。**是否并行执行是宿主的决定**。模型完全不知道也不关心宿主怎么执行。

## 4. 三家 Function Calling 形状差异

同一个四步循环，三家的字段名、嵌套结构、类型约定全不一样：

| | OpenAI | Anthropic | Gemini |
|---|---|---|---|
| 声明 | `tools: [{type: "function", function: {...}}]` | `tools: [{name, input_schema}]` | `tools: [{functionDeclarations: [{...}]}]` |
| 调用位置 | `message.tool_calls[]` | `content[]` 里的 `tool_use` 块 | `parts[]` 里的 `functionCall` |
| 参数类型 | JSON 字符串 | 已解析对象 | 已解析对象 |
| 强制某工具 | `tool_choice: {function: {name}}` | `tool_choice: {type: "tool", name}` | `mode: "ANY"` |
| 严格模式 | `strict: true` 标志 | 无标志，schema 本身就是契约 | 请求级 `responseSchema` |

**协议编码** = 同一件事用不同的格式写出来。字段名、嵌套结构不同，但语义完全一样。

## 5. 并行工具调用

串行查 3 个城市天气：3 次 LLM 往返，总耗时 = 400+600+800 = 1800ms

并行查：1 次 LLM 往返，总耗时 = max(400,600,800) = 800ms

省了 60-70% 时间。代价是关联复杂度——多个调用乱序完成时，靠 `tool_call_id` 把结果和调用对齐。

**不能并行的情况：** 工具之间有顺序依赖（如 `create_file` → `write_file`），或下游限流器扛不住扇出。

## 6. 流式参数重组

模型流式输出时，三个并行调用的 `arguments` 碎片会在同一条流上交错到达。需要一个 **accumulator（累加器）**，按 id 分别缓存碎片，等收到完整 JSON 后才解析执行。

**核心陷阱：不能提前 parse** — `{"city": "Beng"` 不是合法 JSON，要等调用结束信号（OpenAI 的 `finish_reason = "tool_calls"`、Anthropic 的 `content_block_stop`）才解析。

## 7. 工具调用的错误防护

模型生成的 JSON 内容确实可能出错。防护是三层工程化机制：

| 层 | 机制 | 作用 |
|---|---|---|
| Provider 端 | 严格模式（受约束解码） | 从底层物理限制模型不可能输出不符合 schema 的内容 |
| 宿主端 | Schema 验证 | 拿到调用后先验证参数，不合法就拒绝执行 |
| 宿主端 | 错误重试 loop | 把验证失败的原因喂回模型，模型重新生成调用 |

模型生成格式约束的来源：system prompt 里的工具定义（JSON Schema）+ provider 微调 + 受约束解码。不是纯靠提示词"请求"模型遵守格式，而是从训练到解码层层约束。

目标不是消灭错误，是让错误变得可控、可恢复、不会失控。

## 8. 模型回复的顺序

- **工具结果返回** — 顺序可能乱，靠 id 对齐，这是工程问题
- **最终回复用户** — 顺序由模型自主决定，怎么表达好就怎么来，不受原始调用顺序约束

## 9. 关键概念速查

| 概念 | 含义 |
|------|------|
| **工具（Tool）** | 名称 + JSON-Schema 输入 + 执行器函数三元组 |
| **纯工具** | 只读、无副作用；可安全重跑 |
| **后果性工具** | 改变外部状态；需要闸门、审计或用户确认 |
| **熔断器** | 循环最大 turn 数限制（通常 5-20 次），防止无限循环 |
| **Strict Mode** | 受约束解码，强制输出符合 schema |
| **CI** | 持续集成，代码合并时自动跑检查 |
| **心智模型** | 用已知概念理解新概念的认知框架 |
