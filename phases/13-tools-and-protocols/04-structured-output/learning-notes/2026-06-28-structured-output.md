# 结构化输出学习笔记

> 日期: 2026-06-28

## 1. 结构化输出的三种方法

| 方法 | 原理 | 缺点 |
|------|------|------|
| **Prompt** | 自然语言指令要求输出 JSON | 5%-15% 失败率（缺括号、类型错、幻觉字段） |
| **生成后校验** | 生成完再解析校验，失败重试 | 每次重试都要付费，截断类 bug 每次多花一个回合 |
| **约束解码** | 解码时屏蔽无效 token，输出保证合法 | 速度略慢，但省去重试成本 |

核心趋势：从"事后补救"到"事前保证"。约束解码把可靠性与模型规模解耦。

## 2. Logits — 模型的原始分数

模型对每个 token 输出的**原始分数**，表示"下一个 token 应该是什么"的确信度。

```
logits → softmax → 概率 → 采样 → token

logits:     [2.3, 1.8, 0.5, -0.2]
softmax:    [0.47, 0.32, 0.13, 0.08]
采样:       选中 "hello" (概率最高)
```

## 3. 约束解码的工作原理

模型**不知道** token 被屏蔽。流程是：

```
1. 模型基于前面所有 token 计算 logits
2. 解码器读取当前状态，检查 schema，算出合法 token 集合
3. 屏蔽非法 token（logits 设为 -∞）
4. 从合法 token 中采样
5. 模型继续下一步，完全不知道第 2-3 步发生过
```

**每一步都重新计算**，不是提前屏蔽好所有步骤。解码器维护一个 FSM（有限状态机），根据已生成内容动态决定当前步骤的合法 token。

## 4. 为什么是"边生成边屏蔽"而非"提前屏蔽"

Schema 是静态的，但每一步的有效 token 是**动态的**。

```json
{"status": "paid"}
```

- Step 1: 可以输出 `{` 或 `"`
- Step 2: 取决于 Step 1 输出了什么
- Step 3: 取决于前面输出了什么

每一步的屏蔽范围取决于前面生成了什么，所以必须逐步计算。

## 5. Strict Mode

**严格模式**，让 LLM 输出 100% 符合 schema 的机制。

核心原理：在采样前把非法 token 的 logits 设为 -∞，只从合法 token 中采样。

| 场景 | 普通模式 | Strict mode |
|------|---------|-------------|
| 缺少字段 | 可能发生 | 不可能 |
| 类型错误 | 可能发生 | 不可能 |
| 多余字段 | 可能发生 | 不可能 |
| 输出能解析 | 不保证 | 保证 |

## 6. Java 编译时类型检查 vs Zod/Pydantic 运行时校验

| 特性 | Java（编译时） | Zod/Pydantic（运行时） |
|------|---------------|----------------------|
| 检查时机 | 编译前 | 代码执行时 |
| 检查对象 | 代码内部变量 | 外部数据（API、JSON） |
| 错误发现 | IDE 实时标红 | 调用 `.parse()` 时才报错 |
| 能检查外部数据 | 不能 | 能 |

Zod 和 Pydantic 本质相同：**运行时校验外部数据**。区别在于 Python 没有编译时类型检查，所以 Pydantic 的运行时校验承担了双重职责。

## 7. Pydantic 与 Zod 的共同点和差异

**共同点：** 都是运行时校验，都能推导类型。

| 特性 | Zod (TS) | Pydantic (Python) |
|------|----------|-------------------|
| 类型推导 | `z.infer<>` 编译时 | `model_json_schema()` 运行时 |
| Python 场景 | — | 更像"必需"，承担双重职责 |

Pydantic 可以同时用于两种方式：
- 作为 schema 定义传给 provider 做约束解码（第三种方法）
- 单独用来做生成后校验（第二种方法）

## 8. Enum — 限定取值的机制

**枚举**（Enumeration），限定变量只能取预定义的几个值。

```python
{"status": {"type": "string", "enum": ["pending", "paid", "cancelled"]}}
```

作用：把"任意字符串"约束为"几个固定选项"，防止模型输出不存在的值。

## 9. 开放实现 vs 商业 Provider

| | 开放实现 | 商业 provider |
|--|---------|--------------|
| 工具 | outlines, guidance, lm-format-enforcer | 内置在 API 中 |
| 使用方式 | 部署模型时自己配置 | API 参数传 schema |
| 典型用户 | 自建推理服务的团队 | 直接调 API 的开发者 |

开放实现的三种技术：FSM 语法解码、Logit masking + JSON 解析器、Speculative decoding。商业 provider 内部可能用类似技术但不公开细节。
